## 적용한 사용자 결정과 순서

필수 주장에 모순이나 근거 부족이 남으면 해결되지 않은 부분과 필요한 근거를 알리고 완성
설명은 보류한다. 이것을 완성 설명의 H/Q 합격으로 계산하지 않는다. 기존 plugin을 유지하며,
그 경로에서 보류를 입증하지 못하면 출하를 보류한다. 별도 UI/runtime이나 낮아진 합격 기준으로
대체하지 않는다.

OFF는 저장 상태를 바꿔 이후 세션 시작과 새 에이전트의 주입을 막는다. 이미 주입된 내용을
제거하는 기능과 그 테스트는 범위에 없다. `hooks/ttak.cjs`는 이미 이 동작을 하므로 변경하지
않았다. 현재 ON 명령도 저장 설정만 바꾸며, 본문 주입은 다음 `SessionStart` 또는
`SubagentStart`에서 한다. 이번에 세션 중간 즉시 ON 주입을 새로 구현했다고 주장하지 않는다.

## 남아 있는 근본 결함의 재현

`.superpowers/verification-remediation-104/semantic-gaps-before.json`은 다음을 실제 로컬 함수로 재현한다.

1. 거짓 문장에 모든 유효 연결 ID를 붙여도 부모 구조 검사가 수용한다.
2. 초안의 읽기 변수를 바꾸고 새 주장을 추가해도 생성되는 질문 packet이 같다.
3. 출처 전체를 정확히 인용하면서 반대되는 답변을 내도 인용 수신 검사가 수용한다.
4. 실제 known Codex 결과에서 R0002를 `contradicted`로 바꿔도, 재작성에 남은 잘못된
   `T1 still observes A = true`를 거부하지 못한다. 전체 블록의 동일 문자열 비교만으로는 부족하다.

또한 7개의 과거 완성 답변을 `stop_hook_active: true`로 현재 Stop 함수에 재생했다.
H/Q FAIL 4개를 포함해 모두 `no_finding`이었다. 이는 native 재실행이 아니라 검사 함수의
탐지 한계 증거다. 실패 후 중지만 고쳐서는 정확한 답변 보류가 완성되지 않는다.

다음 수정은 문단과 원자 주장을 분리하고 주체·대상·부정·범위·조건·시점을 유지해야 한다.
실제 초안과 요구 사항에서 질문 계획을 만들되, 근거 확인 자식에게 초안과 형제 답변은
보내지 않는다. 유한 모델의 읽기/쓰기·각 단계 상태는 기존 계산기로 직접 대조한다.
출처는 버전·원문 범위·조건을 함께 연결하고, 생성자와 독립된 대조 및 최종 본문 검사를
검증해야 한다. 최종 본문 해시는 승인된 본문의 동일성만 증명하고 진실을 증명하지 않는다.

## Stop 경로 수정

- 교정 1회 뒤에도 탐지된 문제가 남으면 `systemMessage` 경고만 반환하던 경로를
  `continue: false`와 구체적인 `stopReason`으로 변경했다. 추가 교정 루프는 만들지 않는다.
- 잘못된 Stop 입력, 초과 크기, 검사 실패, 사용할 수 없는 근거에도 중지 사유를 반환한다.
- 거부된 현재 turn의 도구 결과를 `unavailable` 상태로 보존한다. 뒤에 정상 결과가 와도
  같은 작업의 실패를 지우지 않는다. 다른 turn을 오염시키지 않는다.
- 만료된 근거도 새 사용자 작업까지 실패 상태를 유지한다. 기존에는 첫 확인 후 파일을
  없애서 다음 확인이 단순한 근거 부재로 바뀔 수 있었다.
- 파일 안전 검사 실패 후 다시 쓰지 않는다. 실패 상태를 쓰는 경로는 부작용 없는 도구
  결과 검증이 거부된 경우에 한정한다. 거부된 원문은 저장하지 않는다.
- 교정 지시는 지원되는 필수 주장을 갖춘 경우 완성 설명을 제공하고, 해결되지 않은 경우
  필요한 근거를 알리며 보류하도록 한다. 이미 제공된 근거를 적용하지 못한 상황을
  사용자의 자료 부족으로 돌리지 않는다.

[Codex Stop 문서](https://learn.chatgpt.com/docs/hooks)는 `decision: block`을 후속 실행으로,
`continue: false`를 중지 결과로 설명한다. [Claude hook 문서](https://code.claude.com/docs/en/hooks)는
중지 사유의 사용자 표시를 설명하지만, MessageDisplay의 변경은 transcript 교체가 아니다.
따라서 이 로컬 프로토콜 출력으로 화면·저장·재개의 일관성을 검증했다고 주장하지 않는다.
현재 plugin의 MCP는 `scenario_review`이며 103 설명 controller는 정상 skill 경로에 연결돼
있지 않다. 연결 없는 별도 진단의 성공을 정상 plugin 성공으로 계산할 수 없다.

## 로컬 검증과 실행 환경 사고

1. 회귀 자료·연결 검사: 2파일 **23 PASS**.
2. 새 Stop 요구를 먼저 적용한 검사: 2파일 **16 PASS / 11 FAIL**. 수정 전 결함 재현이다.
3. 첫 수정 후 26 PASS / 1 FAIL. 남은 실패는 새 실패 상태를 검사하면서 정상 응답만
   기대하는 fixture helper를 호출한 테스트 문제였고, 실패 응답을 명시적으로 검사하도록 고쳤다.
4. Stop·근거·패키지·정밀성·초안·기존 ON/OFF 검사: 6파일 **117 PASS / 0 FAIL / 0 skip**.
5. 전체 Node 시도: 41파일 **436 PASS / 2 FAIL / 0 skip**. 아래 Python 자동 설치가
   출력 오염과 작업 루트 파일 검사 실패를 일으켰다. 전체 통과로 기록하지 않는다.
6. Python 실행 경로 수정 후 관련 7파일: **57 PASS / 0 FAIL / 0 skip**.
   Python unittest **78 PASS**, conformance `--selftest` 정상 종료. native 호출은 없다.
7. 마지막 경계 검토에서 늦게 도착한 첫 근거의 실패 상태 보존과 4개 모델 상한 초과
   검사를 추가했다. 상한 검사의 첫 fixture가 초기 불변식을 위반해 도구에서 거부되는
   문제를 유효한 모델로 고쳤다. 최종 관련 7파일은 **59 PASS / 0 FAIL / 0 skip**이다.

전체 검사에서 Windows `python` 별칭이 Python 설치 관리자를 실행했다. 축소 환경에는
사용자 설치 위치가 없어 작업 루트 `Python/`에 3.14.7을 자동 설치했고, 출력에는 관리자
26.3 업데이트도 보고됐다. 설치를 의도하거나 승인한 작업이 아니었다. 별칭을 사용한 것이
원인이므로 Windows에서는 `TTAK_TEST_PYTHON`에 기존 interpreter의 절대 경로를 필수로
지정하게 고쳤다. `WindowsApps` 별칭과 상대 경로는 실행 전에 거부한다. 환경 전파는
허용 목록을 유지한다. [Python 공식 문서](https://docs.python.org/3/using/windows.html)는
설치 관리자의 자동 설치 동작을 설명한다.

기존 `C:\Users\js\AppData\Local\Python\pythoncore-3.14-64\python.exe`는 2026-07-28부터
존재한 Python 3.14.6임을 파일 metadata로 확인했다. 이 실행 파일을 지정한 TOML 왕복
검사와 Python 검사들은 통과했다. 관리자 업데이트 이전 버전은 관측하지 못해 전역 상태가
원상태라고 단정할 수 없다. 임의로 전역 런타임을 되돌리지 않는다.

새 `Python/` 디렉터리의 재귀 정리는 `shell-guard`의 `ps-recursive-delete` 규칙이
거부했다. 지시는 절대 경로를 제시하고 사용자가 `! <명령>`으로 직접 실행하라는 것이다.
다른 셸·Node·파일 이동으로 같은 삭제 효과를 우회하지 않았다. 이 폴더 때문에 전체
출하 파일 검사는 미해결이다. 테스트 실패를 숨기려고 제외 경로나 검사 예외를 추가하지 않는다.

Windows에서의 이후 실행 예:

```powershell
$env:TTAK_TEST_PYTHON='C:\Users\js\AppData\Local\Python\pythoncore-3.14-64\python.exe'
node scripts/test-local.cjs
```
