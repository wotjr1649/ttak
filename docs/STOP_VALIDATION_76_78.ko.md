# 실제 최종 답변 교정과 수집기 정비 — 76–78

2026-09-10 기준 현재 로컬 후보는 **0.2.0-rc.8**, 출하 판정은 **미충족**이다.
실제 두 호스트에서 Stop 피드백 후 수정 답변까지 이어지는 경로는 관측했다.
그러나 일반 설명 과제의 정밀성 실패가 남아 전체 비교를 시작하지 않았다.

## 실제 실행과 판정

| 기록 | 후보 / 모델 | 확인한 내용 | 판정 |
|---|---|---|---|
| 76 | rc.5 / Haiku | skill·MCP 전달, 실제 Stop 실행 | 비용이 트랜잭션 크기와 무관하다는 단정으로 실패 |
| 77-01 | rc.6 / Haiku | 의도적으로 준 잘못된 한 문장 → Stop 차단 → 수정 답변 → 다음 Stop 완료 | 수정 경로 통과, 일반 과제 품질 점수 없음 |
| 77-02 | rc.6 / Luna high | 최초 final → 실제 hookPrompt → 수정 final → Stop 완료 | 수정 경로 통과, 일반 과제 품질 점수 없음 |
| 77-03 | rc.6 / Haiku | 일반 전문가 과제, 정확한 도구 결과 전달 | 교차 읽기·쓰기 부정, 물리적 순차 실행 단정, 근거 없는 10–30% 수치와 잘못된 SQL 대안으로 실패 |
| 78-01 | rc.7 / Haiku | 정상 ON 정책 전달, 실제 skill·MCP·Stop | 필수 H1–H3와 재시도 비용 Q2 통과. 조건·성능 설명의 정밀성 Q1 미충족 |

78은 이전 교차 의존성 부정과 물리적 순차 실행 단정을 반복하지 않았다.
다만 단일 읽기/쓰기 의존성 감지를 abort 조건처럼 설명하고, 낮은 부하에서는 비용이
무시 가능하며 높은 동시성에서는 처리량이 크게 낮아진다고 구현·워크로드 조건 없이
단정했다. 원래 Q1의 정확한 용어·설명 기준에 따라 전체 품질 합격으로 처리하지 않았다.
Q2의 재시도 비용 설명은 통과로 보존했다. PostgreSQL의 실제 조건과 비용 설명은
[PostgreSQL 18 문서](https://www.postgresql.org/docs/18/transaction-iso.html)를 대조했다.
성능은 의존성 추적·재실행 비용과 명시적 잠금의 비용을 함께 비교해야 하며,
특정 부하의 성능 크기를 위 문서만으로 일반화할 수 없다.

77의 수정 경로 시험은 오류 문장을 일부러 출력하게 한 통합시험이다.
192개 비교 과제의 성공, 개선 반복, 일반적인 사실 정확성의 증거로 사용하지 않는다.
78에서는 Stop이 빈 결과를 반환했으며, 품질 실패를 수정한 관측은 없다.

## 구현과 검증 범위

- `scenario-draft.cjs`: 비용에서 트랜잭션 크기를 배제하는 단정, 명명된 참여자의
  물리적 순차 실행 단정, 행의 교차 읽기·쓰기를 부정하는 표현을 추가 검사한다.
  지원하지 않는 자연어 표현은 여전히 미검증이다.
- `scenario-stop.cjs`: 저장 상태가 ON일 때만 자동 교정한다. 설치만 했거나 OFF·상태
  오류인 경우 개입하지 않는다. rc.8은 이 원칙을 잘못된 입력·초과 입력에도 적용한다.
  한 번의 교정 뒤 오류가 남으면 미검증으로 알리며 반복 차단하지 않는다.
- `scenario-native-audit.cjs`: Haiku의 skill 본문이 tool 결과 또는 호스트가 확장한
  별도 메시지로 전달되는 두 경로를 정확한 본문으로 확인한다. 호출 이름만으로
  전달 성공을 인정하지 않으며 도구 응답은 재계산과 대조한다.
- `collect.py`, `low_models.py`: Haiku의 지원되지 않는 effort 인자를 제거하고
  thinking 요청 설정을 사용한다. 수정 전 답변과 최종 답변을 합치지 않는다.
- `release_runtime.py`: 검토된 번들 MCP와 실행 의존 파일의 정확한 바이트만 허용한다.
  다른 서버·변경된 명령·변경된 구현은 거부한다. 실제 호스트 실행은 Windows Job으로
  제한하고 정상 종료·시간 초과 때 자식 프로세스 정리 여부를 기록한다.
- `low_study.py`: 새 수집기·감사·실행 파일도 freeze한다. 변경되지 않는 입력과
  실행 결과를 분리하고, 내부 도구·Stop 반복을 과제 수와 구분한다.

최종 로컬 검증은 Node **197개**, Python **77개** 통과이다.
Windows 수집기 브리지의 실제 입력 전달·정상 종료·자식 0개도 별도로 확인했다.
rc.8 자체의 새 모델 실행은 없다. rc.7 이후의 추가 변경은 OFF 상태에서의
잘못된 입력 처리이며, 이전 모델 결과를 rc.8의 품질 합격으로 전환하지 않는다.

Codex의 후보 hook 네 개는 설치 파일·명령·해시를 대조한 뒤 정상
`config/batchWrite`로 신뢰 상태를 기록했다. 실험 후 `ttak@ttak-stop77`만 비활성화하고
다른 프로필 설정은 보존했다. Haiku의 임시 ON 저장 파일도 사전 상태로 복구했다.
실행·검사 제한을 우회하지 않았다. Node 검사 한 번은 동시성 상한 누락으로 실행 전에
거부되어, 지시된 `--test-concurrency=1`을 명시한 제한된 검사로 수행했다.

## 호출 장부와 남은 작업

누적 진단은 **705회: Claude 419, Codex 286**이다.
기존 700회와 별도로 이번 추가 상한 6회 중 **5회 사용**, **1회 미배정**이다.
전체 비교용 **516회는 미사용**이다. 내부 모델 응답·도구·Stop 단계와 토큰 사용량은
별도 기록하며, 516은 고정 토큰 비용이나 금액이 아니다.

16과제 × 2반복 × 3조건 × 2호스트 = **192 subjects**와 원래 합격 기준을 유지한다.
전체 비교, Opus/Sol 검증, 게시·출하는 미실행이다.
현재 부족한 것은 권한이나 도구 연결이 아니라 최종 답변의 정밀성에 대한 실측 근거다.
같은 후보를 한 번 더 실행하는 것으로 이 결함이 해결됐다고 보지 않는다.
다음 품질 개입은 구현·조건·성능 단정을 확인할 근거와 연결하고, 지원되지 않는
표현을 그대로 통과시킨 이번 답변으로 먼저 반증해야 한다. 그 변경과 정상 대조 검사를
고정한 뒤 남은 1회가 무엇을 판별할지 정해야 한다.

상세 증거는 로컬 `.superpowers/stop-validation-76/`, `stop-validation-77/`,
`stop-validation-78/`에 있다. 각 plan·원본 결과·중단 판정·후보 snapshot을 보존했다.
이 디렉터리는 ignored이므로 Git의 HEAD만으로 실행 증거를 복원할 수 없다.
