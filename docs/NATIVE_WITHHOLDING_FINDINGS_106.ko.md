## 중단 원인과 수행한 수정

**skill의 완료 조건 충돌.** 기존 skill은 도구 분기에서 완성 설명을 제공하도록 무조건
지시했다. 모든 설명 분기에 필수 요구의 근거를 확인하고 미해결이면 필요한 근거와 함께
보류하는 조건을 적용했다. 수정 후보의 첫 답변에서 보류를 관측했지만, Stop 이후까지
유지되지 않았으므로 이 수정만으로 제품 성공을 선언하지 않는다.

**Claude 설치 경로 가정.** Claude는 버전 `+codex...`를 캐시 디렉터리에서
`-codex...`로 바꿨다. 검증 도구가 버전 문자열로 경로를 조립해 native 시작 전에 실패했다.
중단 후 예약·작업 디렉터리·잔여 소유 프로세스가 없음을 확인했다. 수집기는 정상 설치
metadata의 user 범위·버전·경로를 읽고, 후보 캐시 안의 직접 하위 경로인지와 22개 파일
해시를 검사하도록 수정했다. 검사 기준을 낮추거나 캐시를 직접 덮어쓰지 않았다.

**검사 실패 상태 유실.** 유효한 `unavailable` 기록이 `SessionEnd`에서 삭제되고
`SessionStart/resume` 후 `absent`가 됐다. 현재 수정은 실패 기록을 유지하고 재개 및 새
요청에 이전 설명의 미검증 상태를 전달한다. 새 요청이 시작됐다는 이유로 이전 답변을
검증된 것으로 바꾸지 않는다. 정상적인 이전 계산 근거는 새 작업에 재사용하지 않는다.

**손상된 JSON 때문에 새 작업도 중단.** 기존 코드는 이전 JSON을 먼저 파싱해야 초기화할
수 있어 새 `UserPromptSubmit`에서도 같은 실패를 반복했다. 새 요청에서만, 실제 경로·일반
파일·크기·링크·잠금 검사를 모두 통과한 파일의 잘못된 내용만 새 빈 작업 상태로 교체한다.
거부된 원문은 저장·표시하지 않으며 이전 설명은 미검증이라는 안내를 함께 전달한다.
Stop, 도구 결과, 세션 재개가 임의로 손상된 상태를 정상 근거로 바꾸지는 않는다.

이는 파일 접근·잠금 거부를 우회하는 복구가 아니다. 잠긴 파일, 다중 링크 파일, 크기 초과
파일은 그대로 보존하고 실패를 알린다. 별도의 성공 근거를 만들거나 오류를 삼키지 않는다.

사용자 표시만으로 모델에 실패가 전달됐다고 가정하지 않도록, 해당 수명주기 응답에는
`systemMessage`와 `hookSpecificOutput.additionalContext`를 함께 사용한다. Codex 문서는
SessionStart와 UserPromptSubmit의 additionalContext를 모델 문맥으로 정의한다.
[공식 hook 문서](https://learn.chatgpt.com/docs/hooks#userpromptsubmit)
이 프로토콜과 로컬 검사 통과는 양쪽 호스트의 실제 재개 관측을 대신하지 않는다.

### 다음 구현에서 필요한 완료 상태

내부 결과는 `complete`와 `withheld`를 구분하는 합 타입으로 구성해야 한다. `withheld`에는
미해결 필수 요구와 필요한 근거, 실패 종류를 담고 완성 본문을 허용하지 않는다. `complete`는
모든 필수 요구와 최종 본문에 대응하는 검사 결과가 있을 때만 허용한다. 모델이 반환한
`supported` 또는 `complete` 자체는 승인 근거가 아니다. ID·시도·후보·입력·출처·본문 결합은
호출자가 확인하고, 의미 판단은 별도 검사 대상으로 남는다.

권고하는 실행 계약은 다음 순서다.

1. **시도 등록과 범위 확인.** 정상 `ttak-explain` 실행인지 호스트 이벤트에서 확인하고,
   다른 기능의 응답에 설명 gate를 무조건 적용하지 않는다. 도구를 생략한 설명도 조용히
   완료로 빠져나가지 않는지 검증한다.
2. **필수 요구와 원자 주장.** 실제 본문 범위를 하나의 기준 텍스트에 연결하고, 복합 주장을
   분해한다. `FOR SHARE`와 `FOR UPDATE`, 논리상 순차 결과와 실제 실행 순서처럼 결론을
   바꾸는 조건을 삭제하지 않는다. 단순한 필드 추가로 자연어 분해의 정확성을 보장하지 않는다.
3. **중립적인 독립 질문.** 자식에는 필요한 조건·질문·출처만 전달한다. 부모 초안의 결론이나
   형제 답변은 보내지 않는다. 잘못된 주장에 대한 질문도 기대 정답을 유도하지 않게 구성한다.
4. **직접 계산과 근거 대조.** 유한 모델은 기존 계산기를 재사용한다. 실제 PostgreSQL의 잠금·
   SSI·실측 성능 주장은 유한 모델의 계산 결과로 인증하지 않는다. 지원되지 않는 필수 주장은
   명시적으로 남겨 보류하도록 한다.
5. **재작성 후 최종 검사.** 필수 요구 누락, 남은 반증, 새 사실·조건·보장을 다시 대조한다.
   최종 해시는 검사한 본문의 동일성만 확인한다. 해시를 사실성 점수로 취급하지 않는다.
6. **상태를 집행하는 Stop.** 이미 보류되었거나 검사가 실패한 시도에 단순한 재작성 지시로
   완료를 허용하지 않는다. 최종 본문이 검사한 본문과 다르거나 결정이 없으면 미검증을
   표시하고 완료를 보류한다. 현재의 `consumed`와 ‘정규식 발견 없음’을 완료 허가로 사용하지 않는다.
7. **전달과 재개 검증.** 사용자 본문·중지 사유·native 종료 상태·재개한 대화에서의 상태를
   각각 확인한다. 이전 초안이 남아도 미검증 상태가 명확하고 유지돼야 한다.

이 설계에서도 모델 의미 판단은 오판할 수 있다. 독립 확인을 추가했다는 이유만으로 성공을
가정하지 않으며 정상 대조 손상과 검증자 오판을 함께 측정해야 한다. 대규모 재시도나
정규식의 known 문구 추가를 근본 해결로 채택하지 않는다.

호스트의 시도 범위도 미해결 조건이다. Claude 문서의 skill frontmatter hook은 호출 시
등록되고 세션 동안 유지된다. 따라서 ‘현재 실행 중인 설명에만 적용된다’고 단정할 수 없다.
[공식 skills 문서](https://code.claude.com/docs/en/skills#frontmatter-reference)
같은 기능이 Codex에 그대로 있다고 가정하지 않는다. 현재 고정 호스트에서 정상 호출과
후속 일반 작업을 구분하는 실제 관측이 필요하다. 이 범위를 확정하지 않은 상태에서
새 runtime이나 전역 응답 차단기를 제품에 끼워 넣지 않는다.

## 정산·복원·남은 출하 조건

이번 106의 새 상위 native 시작은 **4회(Claude 3, Codex 1)**다. 활성화 2회 외 실제 모델
세션은 Haiku 2개이며 각각 assistant 응답 3개를 관측했다. 누적은 **825회
(Claude 496, Codex 329)**다. 12회 장부의 미사용량은 **8회**다. 수정 후보에서 남은 9개
검사를 모두 수행할 수 있다는 뜻이 아니며, 실패한 원래 행의 UNRUN을 지우지 않는다.

관측 입력·캐시는 **113,950**, 출력·thinking 포함 수치는 **11,051**, 합계 **125,001 tokens**다.
thinking 내용을 저장하지 않았으며 출력 token 수에 thinking을 다시 더하지 않았다. native가
제시한 목록 가격을 구독의 실제 추가 청구로 해석하지 않는다. API 유료 경로를 사용하지 않았다.

설치·검토·원복 관리 프로세스는 **12/12회**, 모두 모델 호출 없이 종료했다. native 4개와
관리 12개 Job 모두 실행 전 할당·정리 완료·잔여 소유 process 0을 확인했다. Codex는
기존 `ttak@ttak-release` 활성과 `ttak@ttak-stop77` 비활성을 복원했고 시험 후보를 껐다.
Claude 시험 후보도 정상 CLI로 비활성화했다. 양쪽에서 시험 후보가 만든 ON 파일은 모든
시험 세션 종료 후 원래의 ‘없음’으로 복원했다. 캐시·등록·비활성 후보의 신뢰 metadata는
증거와 함께 남겼으므로 설정 파일 전체가 byte 단위로 과거와 같다고 주장하지 않는다.

OFF 후 세션에 이미 주입된 내용을 제거하는 구현·시험은 추가하지 않았다. `hooks/ttak.cjs`는
변경하지 않았다. 로컬 검사의 기존 저장 상태 검사는 이 제외 기능의 native 시험이 아니다.

사용자가 정한 순서에서 1단계인 과거 대조 고정은 완료됐고, 현재는 2단계 정상 plugin 보류
계약의 실패를 해결하는 중이다. 3–6단계의 원자 주장·독립 최종 검사·후보 반복·네 기능과
**192 subjects / 516 requests**는 완료로 표시하지 않는다. 9월 14일 중간 판정과
9월 19일 출하 목표도 이 실패를 면제하지 않는다. 다음 native 실행은 남은 gate 구현과
새 고정 후보·호스트별 수집·정산 계획이 구체화된 뒤 진행한다. 기존 plugin에서 이 계약을
입증하지 못하면 사용자의 결정대로 출하를 보류한다.

근거 디렉터리는 `.superpowers/verification-native-106/`이다. 주요 파일은
`preflight-diagnosis.json`, `rows/*/review.json`, `repairs/*/transcript-audit.json`,
`repairs/*/review.json`, `failure-mechanisms.json`, `lifecycle-manifest.json`,
`full-checks-lifecycle/result.json`, `native-accounting.json`, `restoration-verified.json`이다.
`failure-mechanisms.json`은 수정 전 함수 재생이며 native 재개 실험이 아니다.
