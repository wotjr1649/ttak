# TTAK 개발 일시 중단 브리핑

2026-09-14 KST. 사용자 요청에 따라 개발과 native 실행을 일시 중단했다.
이 문서는 새 개발 계획이나 실행 승인이 아니라, 지금까지의 작업·근거·미완료 원인과 보존 상태를 정리한 사람용 점검 자료다.

## 1. 결론

**TTAK는 아직 전체 출하 기준을 충족하지 못했다. Go가 아니며, 완료로 처리하지 않았다.**
마지막 실행인186번은 이미 CLOSED/RESTORED였다.187번은 설계 문서만 있고 구현·배정·관리·native 시작은 모두0이다.
중단 요청 이후 제품 수정·새 후보 고정·모델 호출·설치·활성화는 하지 않았다. 읽기 전용 대조와 이 브리핑 문서 정리만 수행했다.

미완료의 중심은 설명 기능이다. **독립 사실 검증 → 최종 설명 검토 → 필요한 보류/정정 → 승인된 본문 그대로 전달**하는 흐름을
Haiku와 Luna의 정상 plugin에서 안정적으로 끝내는 데 작업이 계속 집중됐다. 단순 사례에서 부분 성공은 쌓였지만,
원래 복잡한 설명의 품질, 같은 최종 후보의 반복·새 사례·실패/취소/재개, 네 기능 전체와 원래 비교까지 도달하지 못했다.

기술적인 문제가 실제로 있었고, 동시에 제 진행 방식에도 문제가 있었다. 개별 결함의 수정과 감사를 계속 세분화하면서
전체 출하 경로가 얼마나 남았는지에 비해 설명 하위 절차에 과도하게 오래 머물렀다. 로컬 테스트 증가나 개별 배치의 성공을
전체 완료로 포장하지는 않았지만, **개발이 출하 완료로 수렴하지 못한 사실과 그 우선순위 판단은 제 책임**이다.

## 5. 마지막186번을 왜 FAIL로 닫았는가

Luna는 fact 조회 후, 최종 설명 등록/승인 전에 다음 진행 문구를 썼다.

> The independent fact check confirms both reads return 7 and the stored value remains 7 after each read. I’m now running the exact final-text review on that approved wording.

제가 실패로 판정한 부분은 `approved wording`이다. 사실에 대한 답변과 최종 설명의 승인이 구분돼야 하는데,
최종 승인 전에 문구를 승인됐다고 부른 점을 미검증 상태 표시의 명확성 실패로 해석했다.
다만 같은 문장에 최종 검토가 진행 중이라고도 했고, 그 뒤 실제 최종 검토와 정확한 승인 본문 전달은 정상 완료됐다.

따라서 **이 FAIL은 최종 답의 사실 오류나 최종 검토 부재를 뜻하지 않는다.** 기존 미검증 상태 표시 요구를 엄격하게 적용한
표현·승인 범위 판정이다. 이 정도 모호성을 해당 배치의 첫 실질 실패로 취급한 판정 강도와 우선순위는 사용자 점검 대상이다.
그 판정 때문에 예정했던 양 host의 원래 simple 대조2행을 UNRUN으로 닫았다는 점도 분명히 남긴다.
근거: [원래 판정](../.superpowers/release-loop-186/rows/04-codex-delivery/review.json),
[186 상세](NATIVE_RECEIPT_FRAMING_186.ko.md).

별개의 실제 구현 누락도 있다. 공용 `parseNativeReturn`은 단일 unlabeled fence의 compact receipt를 받지만,
Codex 정상 정적 Code Mode 코드의 `nativeDispatchBase`와 `currentSpawnBody`에는 별도의 JSON reader가 남아 있고
아직 bare/json-labelled 형식만 받는다. 로컬 parser 통과를 전체 실제 실행 코드의 호환성 통과로 넓힐 수 없다.
이 누락을 확인한 뒤187에 승인 상태 전달과 reader 계약 일치를 계획했으나, 중단 요청을 받아 구현하지 않았다.

이 표현 문제 하나만 없으면 전체 Go가 되는 것도 아니다. 아래 필수 조건이 별도로 남아 있다.

## 8. 왜 오래 걸렸는가 — 기술적 원인과 진행 방식 평가

### 관측된 기술적 원인

1. **흐름이 길고 모델의 정확한 절차 수행에 의존한다.** 등록, 별도 검증자 시작, 구조화 제출, receipt 반환,
   결과 조회, 최종안 등록, 새 검증, 다시 조회, 원문 그대로 전달 중 어느 하나를 생략·변형해도 실패한다.
   부모의 cache/store 생략, challenge 오복사, 다른 host 옵션 사용, 등록 전 Agent 시작 같은 실제 오류가 있었다.
2. **형식 검사와 의미 정확성은 다르다.** 실제 독립 검증자가 source와 final의 문제를 혼동하거나,
   거짓 근거 부족을 선언하거나, 잘못된 설명을 승인했다. 해시·schema를 더 엄격히 맞춰도 그 의미 문제가 저절로 해결되지 않았다.
3. **양 host의 API와 반환 형식이 다르다.** Code Mode와 Agent의 인계·receipt·도구 metadata·가시 block 구조가 달라
   같은 내부 계약을 각각 맞추는 수정이 반복됐다. 패키지 자체의 범용 검사 호환성은180에야 해소됐다.
4. **검증·정정 경로가120초 안에 끝나지 못했다.** 특히 사실/최초 최종안/정정 최종안의 세 검증과 부모 왕복이 필요한 Luna 교정 흐름에서 반복됐다.
   중립 질문·계산 근거·제출 구조와 실행 코드 최적화를 시도했으나 최종 안정 완료를 입증하지 못했다.
5. **수집·감사 코드 자체의 오류도 있었다.**186에서는 Claude 응답의 non-text block을 빈 final로 오인했고,
   별도의 선택기와3개 검사로 감사 오류를 고쳤다.184/185에는 테스트 fixture와 새 결과 출처의 전제 불일치도 있었다.
   원본 실패를 보존하고 바로잡았지만 그만큼 추가 조사·검사 비용이 들었다.

### 제 진행 방식에서 점검해야 할 문제

- 각 반복에는 새 반례와 변경이 있었지만, **작은 국소 수정80개가 전체 흐름의 안정 완료로 이어지지 않는 상황을 더 일찍 큰 단위로 재평가하지 못했다.**
- 설명 품질을 확보하는 내부 상태·receipt·검토·cache·정적 실행 코드가 늘어나면서, 그 절차 자체를 디버깅하는 일이 목적처럼 커졌다.
  사용자 기능 범위를 늘린 것은 아니지만, 내부 구현 복잡성이 성공 경로와 새 실패 경로를 함께 늘렸다.
- 작은 단위 변경에도 회귀·후보 갱신·정상 설치·native·감사·복원을 반복한 비용이 컸다.
  검사를 약화할 수는 없지만, 모델에 맡길 부분과 결정적으로 처리할 부분을 정하는 구조 판단이 충분히 빨리 수렴하지 못했다.
- 실패한 후보를 출하 비교에 넣지 않는 원칙은 유지했으나, **전체 collector의 포팅 등 독립적으로 준비할 작업도 뒤로 밀렸다.**
  따라서 설명 하나가 통과해도 전체 Go까지 바로 갈 수 없는 상태가 됐다.
-186의 표현 모호성을 배치 전체 실패로 닫은 판단은 실제 최종 사실성/검증 성공과 구분해 검토해야 한다.
  그렇다고 이 판정만 취소하면 남은 H/Q·반복·전체 비교가 통과되는 것은 아니다.
- 현재 근거로 완료율이나 신뢰할 만한 남은 시간을 제시할 수 없다. 단순히 몇 군데만 고치면 끝난다거나 거의 완료됐다고 말하지 않겠다.

즉, 지금의 미완료는 외부 승인이나 인증이 없어 멈춘 문제가 주원인이 아니다.
**설명 경로의 신뢰성·의미 품질이 미해결이고, 그 디버깅에 개발 순서가 과도하게 묶여 전체 출하 검증을 진행하지 못한 문제**다.
현재 실행 중단의 직접 이유는 사용자의 점검 요청이다.

## 9. 보존한 작업과 이번 정리의 검증 범위

중단 문서 작성 전 worktree는 tracked 수정13파일, untracked284파일, staged0이었다.
이 숫자에는 이전 세션에서 이미 존재하던 변경과 새 runtime/검사/문서가 함께 들어 있다.
이번 목표 루프만의 순수 diff라고 해석하지 않는다. ignored인 `.superpowers/` 증거와 `docs/prompts/`는 이 Git 숫자에 포함되지 않는다.
HEAD는 그대로이며 commit·push·merge·게시·배포를 하지 않았다.

기존 소스와 과거 실패·UNRUN·소모 예약·설치 cache·native 원자료는 삭제하거나 덮어쓰지 않았다.
중단 정리에서 추가한 것은 이 브리핑, 전체 배치 색인, 집계/정지 audit JSON과 상태 표시다.
제품33파일을 수정하지 않았고, 전체 제품 테스트 대신 문서 사실·링크·정산·현재 hash/복원·diff를 확인했다.

과거 `RELEASE_DECISION.ko.md`나 `RELEASE.md`의 checkpoint는 당시 후보/라운드 기록이다.
그 안의 과거 버전·누적·진행 상태를 현재값으로 쓰면 안 된다. 현재 정지 상태는 이 문서와
[RELEASE_STATUS](RELEASE_STATUS.ko.md)의 맨 위를 기준으로 확인할 수 있다.

점검할 때 우선 구분할 쟁점은 전체 Go 기준 자체, 미검증 표시의 실제 판정 강도,
모델이 직접 수행해야 하는 절차의 수,120초 안의 교정 가능성, 그리고 출하 collector 준비의 우선순위다.
이 문서는 그 선택을 대신 확정하거나 자동 재개하지 않는다.

**사용자의 명시적인 재개 요청 전까지 개발·native 실행을 진행하지 않는 일시 중단 상태로 남긴다.**
