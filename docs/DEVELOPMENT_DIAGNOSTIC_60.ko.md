# 개발 기능 반복 비교 — 진단 60

2026-09-10. 기존 `develop-safe-trim` 과제로 Haiku·Luna에서 기본 모델과 설치된 TTAK를
각각 두 번 실행했다. 8개 응답 모두 기능 검사를 통과했지만, **TTAK의 반복적인 실질
개선은 확인하지 못했다.** 설명 품질의 기존 실패를 이 결과로 상쇄하지 않는다.

## 조건과 실제 전달

Claude Code `2.1.266` / `claude-haiku-4-5-20251001` / thinking 활성화 및 요청 상한
8192, Codex CLI `0.153.4` / `gpt-5.6-luna` / `high`를 사용했다. Haiku 상한 수치는
요청값이며 세션 로그에서 독립 확인할 수 없다는 기존 한계를 유지한다.

두 호스트의 기존 테스트 프로필과 구독 인증을 사용했다. TTAK는 켜져 있었고 설치된
hook·정책·스킬은 현재 작업 트리와 일치했다. 프로필·전역 설정·신뢰 설정은 바꾸지 않았다.
기본 조건에는 TTAK 정책을 넣지 않았다. 과제는 동일한 전체 fixture를 입력으로 받고
코드만 반환하도록 했으며 모델의 파일·명령·웹 도구 실행은 허용하지 않았다.

`scripts/native-subject-format.cjs`는 실제 모델과 입력을 검증하고, Claude의 SessionStart
hook 추가 문맥과 Codex의 developer 입력에서 전체 TTAK 정책의 전달 여부를 확인한다.
모델의 자기 선언이나 답변 속 정책 복사를 전달 증거로 세지 않는다. 새 검사는 잘못된
모델, 실행 실패·도구 호출, 정책의 자기 복사와 잘못된 입력 역할을 거부한다.
관련 새 검사 3개와 기존 네이티브 검사 11개, 총 14개가 통과했다.

시험 전에 최대 8회, 새 세션, 입력·수집 코드·실행 파일 해시, 원래 hard/quality 기준,
중단 조건을 고정했다. 호출마다 120초·출력 상한·Windows Job 프로세스 정리를 적용했다.
각 결과를 검토하고 결과 해시에 연결된 진행 판정을 남긴 뒤 다음 실행을 시작했다.
8개 세션 ID가 모두 다르고, 모든 네이티브 실행의 자식 프로세스 정리가 확인됐다.

## 기능과 품질 결과

각 응답의 코드 전체와 import를 검토한 뒤 기존 `verify_project.py`의 cleanup 검사를
격리된 Python 시작 옵션과 인증 환경 변수 없는 환경에서 15초 상한으로 실행했다.
미리보기·확인, 루트·범위 밖 경로 거부, 계획만 반환하며 대상 파일을 보존하는 동작을
확인했다. 다른 함수가 바뀌지 않았음도 AST 또는 이미 검토한 동일 파일의 바이트로
대조했다. 이 테스트는 모든 가능한 파일 시스템·호출 조건의 증명은 아니다.

| 호스트 | 반복 | 기본 모델 | TTAK | 사전 품질 기준에 따른 비교 |
|---|---|---|---|---|
| Haiku | 1 | 기능 통과, 불필요한 클래스 제거 | 기능 통과, 클래스 제거 | 동률 |
| Haiku | 2 | 기능 통과, 클래스 제거 | 기능 통과, 클래스 제거 | 동률 |
| Luna | 1 | 기능 통과, 클래스 제거 | 기능 통과, 사용하지 않는 클래스가 남음 | 기본 모델 선호 |
| Luna | 2 | 기능 통과, 사용하지 않는 클래스가 남음 | 기능 통과, 클래스 제거 | TTAK 선호 |

사전 기준의 “불필요한 구조를 실제로 제거”에 따라, 더 이상 호출하지 않는 클래스를
전체 반환 모듈에 남긴 경우를 불완전한 단순화로 기록했다. 이 품질 차이를 기능 검사
실패로 바꾸지는 않았다. 따라서 사전에 정한 중단 조건에 따라 두 번째 반복도 실행했다.

일부 응답은 확인된 계획의 preview/delete가 같은 리스트를 참조하고 다른 응답은
복사본을 만들었다. 고정 과제는 리스트 객체의 독립성을 명시하지 않았으므로 이 차이를
사후 합격·실질 개선 기준으로 추가하지 않았다. Luna에서 유리한 결과가 한 번 있었지만
첫 반복은 반대였으므로 “반복 관측된 개선”으로 인정하지 않는다.

## 보존된 근거와 한계

`.superpowers/development-60/`의 `plan.json`, 각 실행의 `attempt.json`, `process.json`,
`audit.json`, `result.json`, `project.py`, `functional-check.json`, `operator-review.json`과
최종 `comparison.json`이 근거다. 원본 비교와 블라인드 채점은 이번에 하지 않았다.
한 개발 과제의 진단이며 192개 전체 비교나 개발 기능 전체의 합격으로 세지 않는다.
응답별 네이티브 시간과 토큰 필드는 기록했지만 작은 표본으로 효율 우위를 주장하지 않는다.

첫 기능 검사 명령에 잘못된 해시를 넣어 Python 실행 전에 중단된 일이 있었다. 실제로
검토한 파일의 해시로 인자를 바로잡았으며, 모델을 다시 호출하거나 실패 기록을 덮어쓰지
않았다. 이후 8개 파일의 기능 검사와 프로세스 정리는 모두 완료했다.

이번 네이티브 호출은 **8회**다. 누적은 **693회(Claude 410, Codex 283)**, 진단 잔여
**7회**, 별도 전체 비교 배정은 **516회**다. 후속 시험이 잔여 상한을 넘으면 먼저 구체적
범위와 비용을 준비하고 상한 변경을 확인해야 한다. 추가 호출을 자동 승인된 것으로
간주하지 않는다. 제품 코드의 동작 변경, 외부 게시나 상위 모델 시험은 하지 않았다.

다음에는 모델 호출 전에 과거 Luna 리뷰 자료의 재사용 자격을 확인할 수 있다. Luna의
모델·effort가 유지됐다는 사실만으로 재사용하지 않고, 선택한 과제의 실제 지침 전달,
CLI·도구·설정과 현재 후보 입력까지 대조해야 한다. 이는 읽기 전용 감사의 후보이며,
과거 응답을 현재 합격 실적으로 인정하거나 재실행을 승인한 기록은 아니다.
