Claude의 일반 agent·fork·상속·모델·partial·도구 제한 근거는
[Subagents](https://code.claude.com/docs/en/sub-agents)다. plugin agent의 배치와
지원 필드는 [Plugins reference](https://code.claude.com/docs/en/plugins-reference)에서 확인했다.
plugin agent에는 `hooks`, `mcpServers`, `permissionMode` frontmatter가 지원되지 않는다.
따라서 agent 파일에 이를 적어 격리를 달성했다고 판단할 수 없다. 필요한 제한은 실제
지원되는 tool allowlist와 정상 plugin hook 경로에서 구현·검증해야 한다.

Codex의 모델·추론 설정과 부모 설정 상속은
[공식 Subagents 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents),
plugin skill/MCP 진입은 [Plugins 문서](https://learn.chatgpt.com/docs/plugins)에 근거한다.
이 문서에서 `fork_turns`를 찾지 못했으나, 설치 바이너리에서 그 처리 문자열을 확인했다.
문서 검색 부재를 기능 부재로 판단하지 않는다. 현재 세션의 collaboration 도구를
제품 CLI의 실제 tool schema 증거로 사용하지 않았다.

**Codex 정적 조사에서 새로 확인한 차이.** 설치된 실행 파일로
`app-server generate-json-schema --experimental --out <이번 증거 디렉터리>/codex-schema`를
실행하여 JSON schema 426개를 생성했다. app-server를 기동하거나 계정을 조회하지 않았다.

- `ThreadStartParams`에는 모델·config·권한·historyMode 등이 있다. `historyMode` 설명은
  저장되는 이력의 계약이며, 이를 하위 입력 격리 기능으로 해석하지 않는다.
- `ThreadForkParams.excludeTurns`는 응답의 `thread.turns` 생략 옵션이다. **모델의
  상속 이력을 없애지 않는다.** 이 옵션을 검증자 격리에 쓰는 방안은 기각한다.
- `PluginDetail`에는 skills/hooks/mcpServers가 있지만 agents 필드는 없다.
  이는 해당 응답 schema의 한계이지 plugin agent 지원 불가능성의 증명은 아니다.
- `TurnInterruptParams`는 threadId/turnId를 요구한다. `ThreadTokenUsageUpdatedNotification`은
  threadId/turnId와 last/total을 제공한다. 부모·자식 식별과 중복 없는 집계 설계에 사용할 수 있다.
- 해당 thread/turn 시작 schema에는 직접적인 API 응답 횟수·출력 토큰 상한 필드가
  발견되지 않았다. config 등 다른 경로의 가능성은 남지만 강제 상한을 확인했다고 쓰지 않는다.

현재 제품 `hooks/ttak.cjs`는 SubagentStart에 precedence/invariants를 주입한다.
`scripts/scenario-native-audit.cjs`는 자식 없는 기존 연쇄를 가정하므로 그대로 재사용하면
새 경로의 올바른 자식도 거부하거나 사용량을 빠뜨릴 수 있다. 별도 자식 감사가 필요하다.
`scripts/review-native.cjs`는 baseline 프로필의 설정 파일 부재를 요구한다. 이를 정상 설치
제품용 실행기로 재사용하면서 검사를 제거하는 방안은 제외한다.

## 3. 검토할 후보 한 개의 계약

**초안 → 중립 질문 → 질문별 새 문맥의 동일 모델 근거 확인 → 대조 → 완성 설명 수정**이다.
개입은 검증자가 초안의 오류 문장을 평가하는 대신, 그 결론을 보지 않고 사실 질문에
답하는 데 있다. 동일 모델 여러 개의 동의는 독립된 진실 근거가 아니다.
[CoVe 연구](https://aclanthology.org/2024.findings-acl.212/)는 이 가설의 출처이며
Haiku/Luna의 품질이나 정상 plugin 연결을 입증하지 않는다.

| 단계 | 입력과 결과 | 접근 경계·실패 처리 |
|---|---|---|
| 초안 | 원래 과제·독자·허용 근거 → 실제 완성 예정 설명 D0 | 부모만 D0 보유. 필요한 예제·완화책·비용까지 포함 |
| 질문 구성 | 과제 요구와 D0의 중요한 주장 → coverage map, 질문 계획 | 원래 과제 요구를 먼저 매핑하고 추가 주장을 덧붙임. 문단 수를 coverage 보증으로 삼지 않음 |
| 질문 패킷 | 질문 ID·중립 질문·원래 조건·근거 ID/버전/내용/hash | D0, 주장 원문, 정답, 오류 위치, 다른 질문 답변, 부모 session 경로는 제외 |
| 독립 확인 | 매 질문에 새 문맥 하나 → 답·적용 조건·근거 위치·미확인점 | 하나의 문맥에 여러 질문을 순차 투입하거나 이전 agent를 resume하지 않음 |
| 대조 | 부모의 D0/coverage map + 모든 완료 확인 결과 | 상충·근거 부재·해석 불일치는 미해결로 유지. 다수결·self-score 금지 |
| 수정 | 대조 결과 → 독자 맞춤 전체 설명 D1 한 번 | 사실·조건을 보존하며 설명을 완성. 전체 H/Q로 평가하고 새 오류가 있으면 실패 |

구현 검토용 잠정 제한은 **질문 최대 8개, 수정 최대 1회, 자식 동시성 1, 재귀·재개·자동
재시도 0회**로 제안한다. 4개는 확정값이 아니며, 8개도 이번 문서가 실행 권한으로 확정하지
않는다. 서로 다른 예제·구현 조건·완화책·비용 주장을 분해할 여유를 두는 탐색 설계값이다.
중요한 질문이 8개를 넘으면 잘라서 통과하지 않고 해당 후보의 예산/coverage 실패로 남긴다.
질문 수가 많아지는 것이 정확성을 보장하지 않는다.

**중립 질문의 구성.** 원래 과제와 근거에서 식별한 대상·조건을 사용해
메커니즘, 관계, 구현별 조건, 비용, 완화책 조건, 비유의 한계 등 질문 유형을 선택한다.
예를 들어 “SI가 rw 충돌을 탐지하므로 왜 두 쓰기가 허용되는가?”는 초안의 결론을
전제로 하므로 거부한다. “명시한 격리 수준에서 어떤 충돌을 처리하며 이 예제의 읽기/쓰기
집합 사이 관계는 무엇인가?”처럼 묻는다. 이는 질문 설계 예시이며 시험 정답 주입이 아니다.

모델이 작성한 질문 문자열을 그대로 보내는 방식만으로 중립성을 강제했다고 할 수 없다.
첫 구현은 고정 질문 유형과 원래 과제/근거의 식별자에서 패킷을 구성하고, 부모 전용
claim-to-question map을 자식 입력에서 분리하는 방식을 검토한다. 자유 문장 질문·선정
대상에도 결론이 숨어들 수 있어 의미 검토는 별도다. 지원하지 않는 질문 유형이 필수이면
미지원/실패로 남기며 이를 범용 설명 성공으로 보고하지 않는다.

**근거 공급.** 첫 진단에서는 공개 합성 과제와 사전 검토한 근거 번들만 사용한다.
boolean 계산은 기존 finite-scenario 계산을 재사용하고, 구현·버전 조건은 문서 근거를
구분한다. 전체 D0를 포함하는 기존 scenario_review 반환 wrapper를 그대로 자식에 보내지
않고 계산값·허용 근거 필드만 추출한다. 검증자에게 임의 파일 Read나 WebFetch 권한을
주지 않는다. 필요하면 고정 source ID만 받는 로컬 읽기 전용 근거 도구 하나를 제공한다.

제품에서는 사용자가 제공한 자료와 기존 도구로 확인한 근거를 같은 계약으로 수용해야
한다. 부모가 정답·오류 위치를 보충하거나 실행 도중 새 요약을 끼워 넣으면 구성요소
진단으로만 분류한다. 첫 번들 시험을 자동 검색·임의 주제 지원 증거로 확대하지 않는다.
근거 공급이 불가능한 필수 질문을 미확인으로만 끝낸 답변은 원래 과제 합격이 아니다.

**세 오류 경계.** 질문 누락은 원래 요구/D0/질문 map을 전체 답변과 대조해 평가한다.
ID와 필수 필드의 누락은 코드가 거부할 수 있지만 의미상 누락은 코드 coverage만으로
판별할 수 없다. 검증자 오류는 실제 출처와 답·조건을 대조하고, 잘못된 인용 위치·없는
source ID·오판·상충을 별도 기록한다. 최종 수정 오류는 D0→D1의 모든 실질 주장과
완성 설명 H/Q를 확인한다. 마지막 단계의 같은 모델 재독을 새 독립 검증으로 추가하지 않는다.

**제품 영향.** 설명 경로와 혼합 과제의 설명 부분에만 개입한다. 개발·리뷰만 요청한
과제에 새 모델 호출을 추가하지 않는 것이 목표다. 진행 표시는 실제 질문 완료 수와
현재 단계만 표시하고 결과를 받기 전 정확성 확인 완료라고 쓰지 않는다. 인터럽트 후
다른 사용자 턴에 이전 질문 결과를 적용하지 않는다. 이 조건은 후속 회귀로 입증해야 한다.

| 기록 | 관측된 실패 | 후보의 다른 점 / 남은 반례 |

이웃 답변 포함, 임의 경로·URL·tool 이름, 질문 수 초과, 중복/재생/다른 턴 ID,
timeout·partial·cancel 뒤 재개, usage 중복·누락, 저장 경로 traversal·symlink를
정상 사례와 함께 검사한다. host mock은 parser/상태 처리만 증명하며 실제 격리로 세지 않는다.
Node는 `--test-concurrency=1`과 유한 test timeout을 유지한다. 제품 연결 후에는 기존
Node/Python/conformance 전체 검사를 한 번 수행하고 네 기능·혼합 경로를 확인한다.

보안 경계는 초안·문서·모델 결과에서 도구/프로세스 제어로 넘어가는 부분이다.
구체적 악용은 출처 본문이 추가 호출, 다른 transcript 읽기, 외부 전송, 임의 실행을
유도하는 것이다. 허용 필드 기반 패킷, 고정 목적지/실행 파일, 자식 도구 제한,
턴별 유한 장부, 링크/범위 검사를 적용한다. hook·MCP·동적 호출을 바꾸는 P1은
전체 관련 보안 검토와 정상/공격 입력 검사가 필요하다. 거부된 효과를 다른 실행기로 우회하지 않는다.

## 6. 최소 native 증거와 비용 계획

**지금 승인된 새 native 상한은 없다. 아래 수치는 계획 배정이며 강제 상한 확인값이 아니다.**
API 응답 수와 토큰의 강제 제어가 미확인인 상태에서 숫자만 적어 실행을 시작하지 않는다.

P2의 최소 구조는 OFF/ON 두 호스트 4행, host별 성공 1행과 취소 1행 4행이다.
성공 행은 부모 전용 합성 표지를 가진 초안에서 중립 질문 1개를 만들고 새 자식 1개만
실행한다. 표지 미출력만으로 격리를 통과시키지 않고 **실제 하위 입력·상속 지침·도구
목록**을 검사한다. 이 입력을 충분히 관측할 수 없으면 미검증으로 종료한다.
취소 행은 자식이 시작한 뒤 취소하고 완료·partial·오류를 구분하며 부모/자식과 도구
프로세스 정리를 확인한다. 성공 행을 과학적 품질 점수로 세지 않는다.

| 배정 단위 | 상위 요청 | 새 하위 문맥 | 계획상 API 응답 ceiling |
|---|---:|---:|---:|
| P2 OFF/ON | 4 | 0 | 행당 1, 합계 4; 정상 제어는 모델 응답 없이 끝나야 함 |
| P2 성공/취소 | 4 | 4 | 부모 최대 6 + 자식 최대 1, 합계 28 |
| P2 합계 | **8** | **4** | **32** |
| P3 후보 품질 | **12** | 최대 **96** | 부모 최대 8 + 질문당 1, 총 **192** |
| P2+P3 계획 합계 | **20** | 최대 **100** | **224** |

P3은 3종 사례×2호스트×2독립 반복이다. known은 원래 explain-expert,
normal은 87의 no-overlap/불변식 정상 대조, transfer는 87에서 실행하지 않았고 이 후보
조정에 사용하지 않을 과제다. 이미 개발자에게 노출된 transfer는 **블라인드 holdout이
아니다**. 고정 후 오류를 보고 후보/질문/근거를 수정하면 새 후보이며 그 transfer도
다음에는 조정에 쓰지 않은 사례로 재사용하지 않는다. 순서는 known 양쪽 → normal 양쪽
→ transfer 양쪽 → 같은 순서의 2반복으로 한다. 후보의 첫 실행·전달·품질 실패에서
이후 전부 UNRUN이다. 과거 성공을 현재 행에 이월하지 않는다.

CLI 프로세스 시작 횟수는 상위 요청 수와 따로 기록한다. Claude print 방식이면 대체로
요청당 시작 1회지만 Codex는 task-owned app-server 하나에 여러 턴을 보낼 수 있다.
설치·제거·ON/OFF 프로세스도 모델 응답과 별도 장부에 남긴다. 하위 문맥 수를 OS
프로세스 수로 간주하지 않는다. 서버의 재시도·compaction·숨은 추가 응답도 API 계수에
포함해야 하며 미보고값을 0으로 채우지 않는다.

**잠정 자원 envelope.** P2 행당 120초, P3 행당 300초, 종료 확인 10초,
supervisor 여유 20초, 동시 요청 1개, stdout 1 MiB/stderr 64 KiB를 제안한다.
P2 모델 행의 보수적 실행+정리 배정은 8×150초=20분, P3은 12×330초=66분이다.
설치/제거·사람의 품질 검토·로컬 준비 시간은 이 86분에 포함하지 않는다.
유휴 shared daemon에서 실행되는 자식은 이 시간/Job 한계로 회수된다는 보장이 없어
task-owned 프로세스 관계를 먼저 확인해야 한다.

API 응답당 입력 65,536 / 출력 16,384 tokens를 **강제 가능한지 확인할 계획값**으로 둔다.
P2+P3 224응답이면 입력 14,680,064 / 출력 3,670,016 tokens가 산술상 ceiling이다.
이는 예상 소비량이나 실행을 승인할 근거가 아니다. 부모 system/도구 정의·cache와
자식 추론까지 포함한 적용 여부를 확인하지 못하면 **토큰 hard cap 미확인**이다.
응답 완료 후 감시 중단은 이미 진행 중인 응답의 소비를 막는 hard cap이 아니다.
Haiku thinking 8192 역시 요청값이며 실제 적용은 미검증이다.

Claude는 non-cache input/cache creation/cache read/output을 각각 보존하고 thinking
상세를 출력 합계에 재가산하지 않는다. Codex는 thread별 input/output/cached/cacheWrite/
reasoning/total 원필드를 보존하고, cached input과 reasoning이 상위 합계에 포함되는
방식이 확인되기 전 임의 합산하지 않는다. 고유 응답 ID로 중복을 제거하고 부모 rollup과
자식 합계를 대조한다. ID별 usage가 없으면 API 응답 개수나 비용 완전성을 인증하지 않는다.
품질을 통과한 뒤 실제 전체 비용·지연을 측정해 채택을 판단한다. 구독 잔여율이나 금액을
이 토큰 배정에서 추정하지 않는다. 추가 API 과금·대체 모델은 포함하지 않는다.

전체 비교의 기존 **516은 상위 subject/activation 388 + grading 128**이다.
후보가 설명 4과제와 혼합 2과제의 모든 턴에서만 최대 한 번 동작한다면 TTAK의
개입 대상은 보수적으로 (4 + 1 + 3)×2반복×2호스트=32턴, 하위 문맥 최대 256개다.
전체 상위 요청 각각에 부모 API 응답 8개를 배정하는 보수적 산술 ceiling은
516×8+256=4,384응답이다. grader/activation도 이 산정에서 넉넉히 잡았으며 최종
freeze에서 실제 경로별로 줄여 계산해야 한다. 516을 772회로 단순 대체하거나 이 문서를
전체 실행 승인으로 사용할 수 없다. 설명 발동 범위가 달라지면 식부터 다시 계산한다.

## 7. 중단·복원·다음 행동

실행 전 candidate/입력/근거/모델/바이너리/도구 제한/평가 기준의 해시를 고정하고
새 장부만 만든다. 한 슬롯을 외부 실행 전에 예약하며 실패 슬롯을 환불하지 않는다.
전체 입력 노출·모델 불일치·초과 spawn·partial·결과 누락·usage 미회수·정리 미확인·
첫 실질 품질 실패는 중단 사유다. 자동 resume/retry로 완성시키지 않는다.

설치는 기존 작업용 `claude-ttak`/`codex-ttak` 프로필의 **그 시점 상태를 다시 확인한 뒤**
정상 CLI 흐름으로만 진행할 계획이다. 대상은 인계의 `.superpowers/release-run-03/profiles/`
아래 두 프로필이다. 기존 ON·알림·다른 plugin·인증은 보존한다. 정상 제거와 필요한
시험 신뢰 변경 복원을 역순으로 수행하고, task-created 상태만 제거한다. shared daemon
전체를 종료하거나 기존 validation87 helper를 재실행하지 않는다. Job 종료와 child thread
완료·활성 process 0을 함께 확인할 수 없으면 복원 미검증을 보고한다.

**현재 결정은 조건부 보류다.** 새 문맥 검증은 과거와 다른 시험 가능한 가설이다.
하지만 Codex의 정상 plugin 호출·실제 입력/도구 격리·사전 API/토큰 한도·자식 회수의
증거가 없다. 따라서 지금 품질 시험이나 전체 516회를 제안 실행하지 않는다.
다음의 가장 작은 구현 단위는 P0의 순수 패킷/장부/감사 세 모듈과 테스트다.
P0는 제품 hook/skill/프로필/계정/모델 호출을 바꾸지 않고, P1에서 필요한 호스트
제어 지점을 구체화한다. P0 이후에도 해당 경계가 없으면 내장 경로 연결 시험을 보류하고
정확히 어느 조건이 미지원인지 보고한다. 별도 앱/범용 실행기 도입을 자동 대안으로 채택하지 않는다.

9월 11–12일은 이 연결·제어 증거를 확보할 계획이다. 13–14일 품질 판별은 P0/P1과
실행 범위 확인이 완료될 때만 가능하다. 14일에는 통과 후보 유무, 두 호스트 차이,
원래 기준 미달 항목, 19일까지 가능한 출시 형태별 영향을 제시한다. 지금 기능이나
품질을 줄이지 않는다. 15–18일 전체 검증/CI/설치 생애주기/배포물 준비와 19일 판정은
선행 품질 통과와 별도 외부 효과 범위가 충족될 때의 일정이며 성공 보장이 아니다.

## 8. 이번 검사와 보존 기록

새 산출물은 이 문서와
[설계 증거 디렉터리](../.superpowers/independent-verification-design-88/)다.
schema는 설치 바이너리가 생성한 원본이며 hand edit하지 않았다. 제품 전체 테스트는
동작 변경이 없어 재실행하지 않았고, 새 native 연결·취소·품질·독립 블라인드 평가는
전부 UNRUN이다. Node/Python 버전·테스트의 과거 기록과 이번 메타데이터 검사를 구분한다.

로컬 조사 중 Python의 기본 cp949 디코딩 오류를 UTF-8 명시로 수정했다.
첫 zip 대조는 최상위 `ttak/`를 포함한 경로를 현재 루트에 바로 붙여 0개가 일치했다.
archive 이름을 확인한 뒤 고정 prefix만 제거하여 62개를 재대조했다. 최초 기록을
