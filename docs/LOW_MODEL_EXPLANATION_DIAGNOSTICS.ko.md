# Haiku 설명 결함과 예제 표현 변경 시험

2026-09-09. 진단 52·53은 각각 Haiku 1회이며 둘 다 최종 설명 품질에 실패했다.
현재 제품 설명 스킬은 시험 전 바이트로 복구했다. 네이티브 설치 프로필은 수정하지 않았다.

## 시험 조건과 범위

Claude Code `2.1.266`, `claude-haiku-4-5-20251001`, thinking 활성화 및 요청 상한
8192를 사용했다. 기준 과제는 기존 `explain-expert` 그대로다. 제공한 입력은 검토한
TTAK 정책 3개, 설명 스킬, 공개적인 두 의사 과제뿐이다. 도구는 비활성화했다.
baseline 프로필의 새 세션에 본문을 직접 제공한 진단이므로 실제 스킬 활성화·설치
검증이나 전체 비교의 후보 실적으로 세지 않는다. 실제 모델과 정확한 입력 전달,
thinking 블록 존재 및 프로세스 정리는 확인했다. thinking 상한 수치는 세션 기록에서
독립 확인할 수 없다는 진단 51의 한계도 유지한다.

각 실행 전에 입력 해시·과제 hard/quality·호출 1회 상한·실패 시 반복 금지를 기록했다.
답변은 로컬에서 전부 검토했으며 별도 채점 모델 호출은 하지 않았다.

## 진단 52: 새 Haiku에서 기존 본문의 결함 확인

답변의 예제는 A가 B의 on-call 상태를 읽고 B가 A의 상태를 읽는다고 했다.
그러나 뒤에서는 서로의 행을 읽지도 쓰지도 않는다고 설명했다. 서로 다른 쓰기 대상과
교차 읽기를 혼동한 내부 모순이며 write skew의 핵심 설명을 훼손한다.

같은 행을 수정할 때의 write-write conflict도 앞선 트랜잭션이 그 행을 **읽었다**는
사실로 설명했다. Serializable의 두 번째 쓰기가 반드시 거부된다는 단정과 근거 없는
비용 일반화도 남았다. 세 해결책을 제시했지만 오류를 상쇄하지 않는다.

입력·출력·감사·판정은 `.superpowers/haiku-expert-52/`에 보존했다.
이 결과는 Haiku에도 현재 후보의 설명 결함이 존재함을 보여준다. Sonnet의 과거 실패를
Haiku의 실패로 간주한 것이 아니며, 다른 기능이나 모든 Haiku 답변에 일반화하지 않는다.

## 진단 53: 명시적인 사건 표로 바꿔도 모순 재발

수정 가설은 예제의 actor/observation/decision/state-change를 독자에게 보이는 표로
표현하면 뒤의 의존성 설명과 대조할 수 있다는 것이었다. 기존 진단 42의 일반적인
추적 권고와 달리 출력의 예제 표현을 바꿨다. 특정 SQL 정답이나 데이터베이스 규칙은
스킬에 넣지 않았다. 해결책도 요청 범위에 맞춰 하나를 설명하도록 했다.

실제로 사건 표가 출력됐지만 표의 교차 읽기와 뒤의 “상대가 쓰는 행을 읽지 않는다”는
문장이 다시 모순됐다. SSI가 단일 read-write dependency만으로 롤백한다는 서술도
남았다. 따라서 표 출력 여부로 성공을 판정하지 않고 후보를 거부했다.

[PostgreSQL 18의 격리 수준 문서](https://www.postgresql.org/docs/18/transaction-iso.html)는
Serializable이 직렬 실행과 일치하지 않을 수 있는 의존 관계를 감지하고 트랜잭션 실패와
재시도를 요구할 수 있음을 설명한다. 개별 읽기-쓰기 의존성이 있다는 사실만으로 특정한
두 번째 쓰기의 거부를 단정할 수 없다. PostgreSQL의 기본 격리 수준도 Read Committed다.
이 공식 근거는 답변 판정에 사용했으며 모델 입력에 정답으로 추가하지 않았다.

사전 중단 조건에 따라 같은 후보의 재시험과 Luna 시험을 하지 않았다.
`.superpowers/explanation-trace-53/`에 가설, 이전 본문, 거부된 본문, 판정을 보존했고
`.superpowers/haiku-trace-53/`에 실제 실행 증거를 남겼다. 이전 본문 해시가 일치하는지
확인한 뒤 정확히 복구했다.

## 다음 설계에 반영할 증거

Haiku가 필요한 관측을 표에 표현해도 후속 설명에서 반대 주장을 생성한다. 표의 존재,
문단 수, 범위 검사나 또 다른 일관성 지시만으로 이 결함이 해소됐다고 볼 수 없다.
이는 지식 부족만으로 원인을 확정하는 증거도 아니다. 입력에 대한 설명 합성과 검증을
분리해 검토할 이유는 있지만 기존 독립 검토가 성공한다는 증명은 아니다.

다음 모델 시험은 추가 지침의 표현 변경을 반복하기 전에, 기존 검토·수정 경로가 이
명시적 모순을 찾아 최종 답변에서 제거하는지와 전체 호출 비용을 함께 구체화해야 한다.
기존 중단 장부나 미확인 주장 검증을 약화해서 진행하지 않는다. 제품 개선안은 아직
선정·입증되지 않았으며 전체 비교를 시작할 조건을 충족하지 못했다.

누적 CLI 호출은 **679회(Claude 400, Codex 279)**다. 이번 2회를 포함해 진단 잔여는
**21회**, 별도 전체 비교 상한은 **516회**다. 호출 수는 구독 잔여율이나 금액이 아니다.

## 진단 54: Haiku 독립 검토 연결과 첫 보고서 실패

후속 작업에서 네이티브 검토 연결부에 명시적인 `haiku-luna` study를 추가했다.
기본값인 과거 Sonnet 경로는 유지한다. Haiku의 정확한 ID, thinking 요청, 실제 thinking
관측을 확인하며 모델 혼입, 지원하지 않는 effort, 도구 호출, 잘못된 인용을 거부한다.
기존 uncertainty·수정·재검토 기준은 바꾸지 않았다. 추가 3개를 포함한 관련 Node
테스트 66개가 통과했다. 처음 테스트 명령의 동시성 상한 누락은 훅이 차단했고,
안내된 `--test-concurrency=1`을 사용해 정상 실행했다.

진단 52 답변은 실제 tokenizer 기준 15문단, 진단 53 답변은 14문단이다. 문단별
검토·1회 수정·같은 수의 전체 재검토는 각각 31회와 29회여서 잔여 21회를 넘었다.
두 역할 경로는 동일 범위에서 최대 5회이므로, 새 Haiku 모델과 진단 52 초안으로
근거·문맥 검토, 가능한 경우 수정·재검토까지 최대 5회인 별도 시험을 고정했다.
진단 49의 중단 장부를 재개하지 않았다. 모델 입력의 근거는 앞서 확인한 PostgreSQL
공식 문서의 검토된 요약이며, 실제 설치나 자동 근거 수집 검증으로 세지 않는다.

첫 근거 검토 1회 뒤 `foreign_role_quote`로 중단됐다. 15문단의 보고는 반환했지만
U012와 U013의 인용문에 원문에 없는 생략 부호를 넣어 서로 떨어진 문구를 합쳤다.
정확한 원문 인용 검증이 이를 거부했다. 실제 모델·입력·thinking·프로세스 정리는
확인했으며 29.479초, 종료 후 active process 0개였다. 문맥 검토나 수정은 실행하지 않았다.

보고서 전체를 로컬 검토하니 인용 형식 외에도 문제가 남았다. U009의 잘못된 인과
설명을 supported로 인정했고, U012에서는 근거 부족을 직접적인 반증으로 취급했다.
U013에서는 제공된 요약에 있는 locking-read 동작을 없다고 했다. 최종 결과는 supported
1개, contradicted 2개, not_established 5개였지만 유효한 검토 보고로 인정하지 않는다.

원문 구간 ID를 선택하게 하는 방식은 인용 복사 오류의 대안으로 검토할 수 있다.
그러나 인용 위치가 정확해져도 위의 의미 판단 오류나 미확인 주장이 해결되지는 않는다.
따라서 인용 방식을 바꾸는 것만으로 수정 경로가 완성된다고 가정하거나 거부된 보고를
보정해서 재개하지 않는다. `.superpowers/haiku-role-54/`에 원본 보고, 실패, 별도 사후
판정과 입력·실행 해시를 보존했다.

최신 누적 호출은 **680회(Claude 401, Codex 279)**, 진단 잔여 **20회**다.
전체 비교 516회는 미사용이며, 제품 품질과 검토·수정 경로는 아직 미완료다.

## 진단 55: 원문 구간 ID 적용과 문맥 범위 누락

[원문 구간 ID 연결부](REVIEW_ANCHORS.md)를 구현했다. 모델이 선택한 시작·끝 ID로
코드가 원문의 연속 구간을 복원한다. 수정도 검증된 오류 위치의 ID로 선택한다.
기존 인용·전체 범위·미확인 주장·수정 검증은 유지한다. 새 표현 방식의 테스트 8개를
추가했으며, 개별 관련 검사 43개와 관련 전체 회귀 검사 74개가 모두 통과했다.

진단 54와 동일한 Haiku·초안 전체·근거로 최대 5회인 별도 시험을 고정했다. 첫 근거
검토는 15문단과 정확한 원문 인용 검증을 통과했다. 그러나 문맥 검토는 필수 15문단 중
7문단만 반환해 `incomplete_anchored_report`로 거부됐다. 2회 후 중단했으며 수정·재검토는
미실행이다. 누락 문단을 코드로 채우거나 실패 보고를 바꿔 실행을 계속하지 않았다.

반환된 판단도 전부 읽었다. 근거 보고는 특정 두 번째 쓰기가 거부된다는 설명과 성능
영향을 과하게 인정했고, 문맥 보고는 U010의 교차 읽기 모순을 놓쳤다. 따라서 이번
개선은 첫 보고의 인용 구성에 한정되며, 최종 설명의 정확도 개선 증거가 아니다.
표현 방식을 더 제약하는 것만으로 의미 오류까지 해결될 것이라고 가정하지 않는다.

`.superpowers/haiku-anchors-55/`에 양 보고의 원본, 실행·실패 기록과 사후 판정을 보존했다.
두 실행 모두 프로세스 정리와 active process 0개를 확인했다. 최신 누적은
**682회(Claude 403, Codex 279)**, 진단 잔여 **18회**, 전체 비교 배정 **516회**다.

## 진단 56·57: 범위 축소 실패와 기본 모델 확인

진단 56은 생성된 답변의 원본 U005와 U010만 바이트를 보존해 새 검토 입력으로 묶었다.
명시적인 교차 읽기와 이를 부정하는 문장을 두 문단에서 찾을 수 있는지 보는 최대
1회짜리 원인 분리 시험이다. 사람이 고른 알려진 오류 구간이며 전체 과제·답변·자동
위치 선정의 검증이나 출하 실적으로 세지 않는다. 외부 근거 없이 예제 자체를 전제로 삼았다.

Haiku는 유효한 두 문단 보고를 반환했으나 교차 읽기를 부정하는 문장을 consistent로
판정했고, 근거로 교차 읽기가 명시된 문장을 연결했다. 이유에는 한 명 이상이 off-call이면
계속 근무할 의사가 있어야 한다는 조건을 위반한다는 별도 논리 오류도 있었다. 따라서
범위를 좁히는 것만으로 검토 정확도가 해결된다는 가설을 거부했다. 정상 대조나 같은
입력 재시험은 하지 않았다. `.superpowers/haiku-scope-56/`에 판정과 원본 보고를 보존했다.

진단 57은 아직 없던 새 Haiku 기본 모델 관측을 확보했다. 같은 원래 전문가 과제만
보내고 TTAK·원본 스킬 지침은 추가하지 않았다. 동일 모델·thinking 요청으로 최대 1회,
자동 재시도 없이 실행했다. 정확한 입력과 실제 모델, thinking 존재, 프로세스 종료를
확인했지만 전체 고정 비교의 반복 관측으로 세지 않는다.

기본 답변은 교차 읽기와 별개의 쓰기 대상을 올바르게 구분했다. 그러나 추가 해결책의
`SELECT doctors WHERE ... FOR UPDATE`에는 의사 행을 선택할 FROM 절이 없어 주장한
행 잠금을 구현하지 못한다. SSI와 잠금 선택에 관한 설명에도 조건·의존성·재시도에
대한 불명확한 서술이 남았다. 기본 모델을 합격으로 판정하지 않았다. 단일 관측이므로
지침이 결함의 원인이라고 단정하거나 Haiku의 일반적인 능력 부족을 증명하지도 않는다.
`.superpowers/haiku-baseline-57/`에 답변·감사·사후 판정을 보존했다.

이 두 결과는 현재 독립 검토 경로를 더 많은 호출로 확장할 근거를 주지 못한다.
제품 설명의 미해결 상태를 유지하며 단순 반복·문구 보강·검사기 확대를 다음 해결책으로
자동 채택하지 않는다. 최신 누적은 **684회(Claude 405, Codex 279)**, 진단 잔여
**16회**, 전체 비교 배정 **516회**다. 이번 턴의 제품 코드 변경은 없다.

## 진단 59: 생성 전 공식 근거 제공도 실패

준비 58은 모델 호출 없는 입력 고정 작업이었다. 이어 진단 59에서는 현재 정책·설명
본문과 원래 전문가 과제에 PostgreSQL 18 격리 수준의 일반 동작 요약을 추가했다.
사후 검토 대신 처음 답변을 만들 때 지식을 제공하는 경로를 새 Haiku에서 최대 1회로
확인했다. 원본 문서는 다시 확인했으며 두 의사 예제의 정답이나 오류 위치는 요약에
넣지 않았다. 사람이 선정·검토한 요약이므로 자동 검색이나 실제 설치 검증은 아니다.

실제 모델·입력·thinking 존재·프로세스 종료는 확인했지만 답변은 실패했다. 본문은
읽기 B/쓰기 A와 읽기 A/쓰기 B인 SQL을 보여준 뒤 서로의 읽기 대상에는 쓰지 않는다고
설명했다. 또한 Repeatable Read에서 양 행을 잠그는 대안을 제시하고 재시도가 필요
없다고 했다. 제공한 [공식 동작 근거](https://www.postgresql.org/docs/18/transaction-iso.html)는
스냅샷 이후 변경된 대상에 대해 트랜잭션이 실패할 수 있고 전체 재시도가 필요함을
명시한다. 이는 단순한 출처 부재가 아니라 제공한 근거와의 불일치다.

`.superpowers/haiku-grounded-59/`에 원본 답변, 실제 입력, 출처 선정 범위, 실행 감사와
실패 판정을 보존했다. 동일 입력 재시험이나 제품 통합은 하지 않았다. 다음에는 다른
필수 기능의 기본 모델 대비 비교에 필요한 설치 상태와 실행 경로를 점검한다. 설명
실패를 다른 기능의 결과로 상쇄하거나 전체 품질 기준을 낮추지 않는다.

최신 누적은 **685회(Claude 406, Codex 279)**, 진단 잔여 **15회**, 전체 비교 배정
**516회**다. 전체 비교와 출하 판정은 미완료다.

## 진단 63: 계산 결과의 설명 과정에서도 오류

사람이 만든 두 상태·두 트랜잭션 입력을 모듈 62로 계산한 뒤 현재 설명 지침 및 원래
전문가 과제와 함께 Haiku에 제공했다. 최대 1회, 재시도 없이 실행했고 실제 모델,
정확한 입력, thinking 존재 및 프로세스 정리를 확인했다. 시나리오 자동 작성이나
네이티브 도구 사용 시험은 아니다.

답변은 교차 읽기·쓰기를 올바르게 설명했지만 `guard_false`를 트랜잭션 abort로 바꿨다.
또한 입력의 `all_possible_interleavings_checked: false`에도 모든 interleaving을
검사했다고 명시했다. 따라서 실패로 판정하고 동일 입력 재시험은 하지 않았다.
`.superpowers/haiku-computed-63/`에 원본 답변과 감사·판정 근거를 보존한다.

후속 로컬 구현은 계산 결과에서 핵심 설명과 검증 범위를 직접 생성한다. 조건이
거짓이라 변경하지 않은 경우와 쓰기 충돌 중단을 구분하고, 완화책에는 스냅샷 획득부터
전체 트랜잭션을 조정해야 한다는 조건을 포함한다. 읽기 전용 `scenario_explain` 도구와
기존 통신부를 함께 검증한 20개 테스트가 통과했다. 설치 제품이나 네이티브 호스트에는
아직 연결하지 않았으며 모델 입력의 충실성과 최종 전달 정확도는 별도 검증 대상이다.

최신 누적은 **694회(Claude 411, Codex 283)**, 진단 잔여 **6회**, 전체 비교 배정
**516회**다. 제품의 설명 필수 품질과 반복적인 기본 모델 대비 개선은 아직 미입증이다.
