# 실제 모델 검증 84 — Claude 도구 응답 형식 불일치

[진단 86](NATIVE_DIAGNOSIS_86.ko.md)은 실제 훅 응답 형식이 문자열인 경우의 거부를 확인했다.
84의 중간 `content`를 배열로 본 정적 분석보다 이 실제 경계 관측을 우선한다.

후속 확인: [검증 85](NATIVE_VALIDATION_85.ko.md)에서도 rc.12의 실제 근거 저장이 실패했다.
아래 배열 호환성 수정의 로컬 결과는 유지하지만, 이를 실제 실패의 충분한 원인과 해결로
판단한 부분은 불충분했다. 실제 실패 단계는 아직 확정하지 못했다.

판정은 **No-Go**다. 승인된 새 12회 검증에서 양쪽 OFF/ON 네 행은 통과했지만,
첫 Haiku 설명 과제에서 필수 교정이 시작되지 않았다. 5회 사용 뒤 장부를 중단했고
나머지 7회는 미실행이다. 중단 뒤 원인을 로컬에서 수정한 `0.2.0-rc.12`는
실제 모델 검증을 받지 않은 후속 후보다. 한 번의 교정이 정밀성·정상 답변·비용을
개선한다거나 원래 네 기능의 출하 기준을 충족한다는 증거는 아직 없다.

## 실행 범위와 관측

사용자의 다음 검증 진행 확인에 따라 [출하 준비 83](RELEASE_PREPARATION_83.ko.md)의
제안대로 새 장부를 만들었다. 시험 후보는 `0.2.0-rc.11+codex.20260910175056`으로
고정했다. 설치 바이트와 수집기까지 포함한 상대 `require` 경로 37개 파일의 바이트,
CLI 실행 파일 해시와 과제를 모델 호출 전에 보존했다.

Windows에서 Claude Code `2.1.266`, Codex `0.154.0`, Node `24.19.0`을 사용했다.
모델은 `claude-haiku-4-5-20251001`과 `gpt-5.6-luna`를 유지했다.
Haiku thinking 8192는 요청값이며 실제 한도 적용까지 확인한 값은 아니다.
Luna는 high 설정을 확인했다. 기존 작업용 구독 프로필을 사용했고 API fallback과
추가 검토 모델은 사용하지 않았다.

Codex는 각 요청의 `thread/start` 전에 실제 `config/read`와 `hooks/list`를 확인했다.
이전 두 플러그인이 비활성이고 검토한 후보의 여덟 핸들러만 정상 신뢰 상태임을 확인한
뒤 요청했다. 별도의 선행 조회는 모델 요청 0회였다.

| 요청 | 관측 | 판정 |
|---|---|---|
| `01.haiku.off` | 정상 훅이 명령을 소비하고 `enabled:false` 저장, 모델 턴·토큰 0 | PASS |
| `02.haiku.on` | 새 CLI에서 명령 소비, `enabled:true` 저장, 모델 턴·토큰 0 | PASS |
| `03.luna.off` | 후보 선택과 훅 확인, `enabled:false` 저장, assistant·도구 항목 없음 | PASS |
| `04.luna.on` | 후보 선택과 훅 확인, `enabled:true` 저장, assistant·도구 항목 없음 | PASS |
| `05.haiku.known1` | skill·scenario 도구·계산 결과·구현 근거 2개 전달, 근거 저장 실패, Stop 교정 없음 | DELIVERY_FAILURE |
| `06.luna.known1`부터 `12.luna.known2` | Luna 전문가·양쪽 미사용 사례·양쪽 정상 사례·양쪽 전문가 반복 미호출 | UNRUN |

이번 **5회(Claude 3/Codex 2)**를 더한 누적은 **715회(Claude 426/Codex 289)**다.
제어 요청도 계수한다. Codex 제어 응답은 토큰 사용량을 보고하지 않았으므로 토큰 0으로
확정하지 않는다. 84의 미실행 7회, 83의 9회, 80의 3회는 재사용하지 않았다.
전체 비교 **192 subjects / 516 requests**는 여전히 미실행이다.

Haiku 설명 요청은 24,275ms가 걸렸다. 기록된 사용량은 입력 18, 캐시 생성 입력 14,651,
캐시 읽기 입력 12,341, 출력 1,873 tokens다. 출력 상세의 thinking 710은 출력과
별도로 더하는 값으로 취급하지 않는다. 고유 API 응답 두 개의 수치도 보존했다.
교정이 실행되지 않았으므로 이 값으로 교정의 추가 시간·토큰을 추정할 수 없다.

실제 `PostToolUse`는 근거를 저장하지 못했다는 메시지를 반환했고 `Stop`은 `{}`를
반환했다. blocking feedback과 수정 답변이 없다. 따라서 원답의 일부 내용이 맞더라도
이번 후보의 필수 교정 경로를 통과했다고 판단할 수 없다. 의미 품질 H/Q의 출하 판정은
별도로 확정하지 않았으며, 이 전달 실패를 Q1 의미 오류 판정으로 바꾸지 않는다.

## 원인과 최소 수정

제 구현은 두 호스트의 `PostToolUse.tool_response`가 전체 MCP 결과 객체라고 가정했다.
설치된 Claude Code 실행 파일의 정적 호출 경로에서는 MCP의 `content`가 도구 `data`로
반환되고, 이 값이 `PostToolUse.tool_response`에 전달된다. 따라서 이 호스트에서는
`content` 배열을 처리해야 한다. Codex의 전체 MCP 결과 형식도 계속 지원해야 한다.
이는 실행 파일 해시에 결합된 정적 경로 확인이며, 실제 hook stdin을 캡처한 증거는 아니다.

`hooks/scenario-evidence.cjs`는 배열을 `{ content: 배열 }`로 정규화한 뒤 기존과 같은
대조를 수행하도록 수정했다. 정확한 입력 키, 단일 text block, 재계산 결과의 완전 일치,
객체 형식의 오류 상태와 structured 결과 일치 검사는 유지했다. 원문 초안·식별자·프롬프트·
transcript 경로를 저장하지 않고, 정규화된 유한 모델만 저장하는 경계도 유지했다.

실제 수집한 도구 입력과 검증된 출력으로 두 호스트의 컨테이너를 구성해 로컬 재생했다.
호스트 컨테이너를 재구성한 검사이므로 실제 native 재실행과 구분한다.

| 재생 입력 | 고정 rc.11 | 수정 rc.12 |
|---|---|---|
| 전체 MCP 결과 객체 | 첫 Stop 교정 요청, 두 번째 요청 없음 | 동일 |
| Claude content 배열 | 근거 저장 실패, 교정 없음 | 첫 Stop 교정 요청, 두 번째 요청 없음 |
| 내용이 변조된 배열 | 거부 | 거부 |

새 회귀 검사에는 빈 배열·추가 block·잘못된 block 종류·변조된 계산값 거부와
실제 패키지 명령의 배열 입력 → 근거 저장 → 한 번의 Stop 흐름도 포함했다.
문구 패턴을 추가하거나 판정 기준을 낮춰 실패를 통과시키지 않았다.

## 로컬 출하 준비와 복원

수정 후 `node scripts/test-local.cjs`로 Windows의 **Node 219개 / Python 78개 /
conformance selftest**가 모두 통과했다. Node 22개 테스트 파일은 동시성 1로 실행했으며
skip은 없었다. Python은 `3.14.6`을 사용했다. 실제 수집 결과의 로컬 재생 여섯 조합도
통과했다. 원격 CI와 다른 OS·Node 버전의 실행 결과는 이번에 얻지 않았다.

양쪽 manifest를 `0.2.0-rc.12`로 맞추고 라이선스·귀속 고지·문서 링크를 포함한 로컬
검토 패키지를 만들었다. 이전 rc.11 패키지와 84의 고정 시험 입력은 보존했다.
새 후보를 설치하거나 native 모델로 실행하지 않았으며 공개 등록·push·publish도 하지 않았다.
배포 채널의 등록 검증과 전체 비교 합격은 아직 필요하다.

시험 설치와 마켓플레이스는 정상 CLI로 제거했다. 설치 전후 플러그인 목록이 일치했고,
이번 Codex 신뢰 기록 여덟 개만 정상 `config/batchWrite`로 제거해 기존 설정과 대조했다.
이번에만 생긴 빈 Claude 설정과 Codex ON 상태 파일을 원래의 부재 상태로 되돌렸다.
기존 Codex `.notified` 표식과 2026-09-08에 기록된 기존 TTAK ON 상태는 보존했다.
각 native 요청과 프로필 작업의 Windows Job 종료·잔류 프로세스 0을 확인했다.

첫 프로필 스냅샷 시 기존 훅 설정에 `enabled`가 생략된 경우를 검사기가 거부했다.
설정 변경이나 모델 호출 전의 준비 실패였으며, 실제 형식을 확인한 뒤 생략을 그대로
보존하도록 스냅샷 검사만 수정했다. 제품 실패 및 성공한 검사 기록과 함께 보존했다.

## 다음 단계 제안

권고는 추가 모델 없이 rc.12의 같은 제한 검증을 새 장부에서 수행하는 것이다.
상한은 **12 native requests: OFF/ON 4회 + 고정 품질 8회**다. 설치 바이트, 실제 후보 선택,
신뢰된 훅, 이번에 확인한 두 호스트 입력 형식의 로컬 재생을 선행 조건으로 둔다.
품질 순서는 Haiku known1, Luna known1, Haiku unseen, Luna unseen, Haiku normal,
Luna normal, Haiku known2, Luna known2다. 과제·H/Q 기준은 84와 같다.

각 품질 행은 도구 출력 전달, 필수 Stop 한 번과 완성 답변, H/Q를 순서대로 확인한다.
정상 답변의 불필요한 수정과 추가 시간·토큰도 관측한다. 첫 실행·전달·실질 품질 실패에서
뒤 행을 중단한다. 새 확인 전에는 실행하지 않으며 중단된 84 장부와 전체 비교 516회를
재개하지 않는다. 이 검증을 통과해도 네 기능 전체의 기본·원본 대비 개선이 입증되는 것은 아니다.

고정 입력, 사용량, 판정, 재생 결과와 복원·전체 검사 로그는 이 worktree의
`.superpowers/native-validation-84/`에 있다. 후속 패키지는 그 아래 `dist/`에 보존한다.
이 경로는 ignored이므로 HEAD만으로 이 실행을 재현할 수 있다고 주장하지 않는다.
