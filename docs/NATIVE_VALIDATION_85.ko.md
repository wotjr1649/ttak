# 실제 모델 검증 85 — 필수 교정 실패 재현과 진단 전환

후속 확인: [진단 86](NATIVE_DIAGNOSIS_86.ko.md)의 실제 단계 기록에서 문자열 응답의
`unverified_tool_result`를 확인했다. 턴은 초기화돼 있었다. 아래의 원인 미확정 상태는
85 시점의 기록이며, 이후 별도 문자열 처리 수정안을 준비했다.

판정은 **No-Go**다. 사용자가 rc.12의 새 12회 검증을 확인해 실행했지만,
양쪽 OFF/ON 네 요청 뒤 첫 Haiku 설명에서 필수 근거 교정이 다시 실패했다.
**5회 사용·7회 미실행으로 중단**했다. 관측된 한 번의 수정 답변은 기존 비용 오류
감지 경로에서 나왔으며, 이번에 검증하려던 필수 근거 교정의 성공으로 세지 않는다.

84에서 고친 응답 배열 호환성은 로컬에서 확인했지만, 그 수정으로 실제 실패 원인을
해결했다는 판단은 불충분했다. 실제 실패 단계는 아직 확정하지 못했다. 제품 동작을
추정으로 다시 수정하지 않고, 제한된 단계 정보만 남기는 별도 진단 사본을 준비했다.
이 사본은 설치하거나 native 모델로 실행하지 않았다.

## 고정 조건과 실행 결과

시험 후보 `0.2.0-rc.12`의 제품 파일은 [검증 84](NATIVE_VALIDATION_84.ko.md)에서
준비한 바이트와 일치했다. 별도 로컬 설치 원본과 새 장부를 만들었으며,
과제·수집기·상대 require 경로까지 37개 파일 및 실행 파일 해시를 호출 전에 고정했다.
이전 설치 원본·패키지·중단 장부는 변경하지 않았다.

Claude Code `2.1.266`, Codex `0.154.0`, Node `24.19.0`을 사용했다.
모델은 Haiku `claude-haiku-4-5-20251001`, Luna `gpt-5.6-luna` high로 유지했다.
Haiku thinking 8192는 요청값이며 실제 한도 적용은 미검증이다.
기존 작업용 구독 프로필만 사용했고 API fallback·추가 검토 모델은 사용하지 않았다.

설치 파일 대조, 정상 훅 신뢰 검토 여덟 개, Codex의 실제 `config/read`·`hooks/list` 조회,
두 호스트 응답 형식의 재생을 통과했다. Codex는 각 `thread/start` 전에도 후보만
활성 상태인지 확인했다. 준비 과정의 조회는 모델 요청을 하지 않았다.

## 전달 경로와 최종 답변을 구분한 판정

Haiku에는 정상 skill, 정확히 재계산한 scenario 도구 결과와 구현 근거 두 개가 전달됐다.
그러나 `PostToolUse`는 근거를 저장하거나 사용할 수 없다는 메시지를 반환했다.
첫 완성 답변에 비용을 단정하는 문장이 있어 기존 `reviewFinalScope` 검사가 Stop을
한 번 차단했다. 차단 이유에는 비용 주장 검토가 있었고 필수 근거 대조 요청은 없었다.
이후 완성 답변과 두 번째 Stop `{}`가 관측됐다. 따라서 수정 답변이 있다는 사실만으로
필수 교정 전달을 통과시킬 수 없다.

Root가 원래 H/Q 기준으로 최종 답변을 검토했다. 독립 블라인드 채점은 아니다.

| 기준 | 판정 | 근거 |
|---|---|---|
| H1 | PASS | 두 트랜잭션이 상대 의사의 기존 ON 상태를 읽고 guard를 통과하는 설명 |
| H2 | PASS | 서로 다른 행을 쓰면서 둘 다 OFF가 돼 불변조건을 위반하는 예시 |
| H3 | PASS | Serializable을 유효한 완화책으로 제안; 구현 설명 오류는 Q1에 기록 |
| Q1 | FAIL | PostgreSQL SSI의 위험 구조를 실제 의존성 cycle과 동일시하는 일반 설명 |
| Q2 | PASS | 의존성 추적 및 전체 트랜잭션 재시도의 비용 설명 |

PostgreSQL의 실제 SSI는 인접한 두 rw-conflict의 위험 구조와 순서 조건을 검사한다.
이 구조가 실제 cycle의 일부가 아닌 경우도 있어 보수적 중단이 가능하다. 최종 답변의
cycle 중심 설명은 이 구현 차이를 정확히 전달하지 못했다.
[PostgreSQL 18 SSI 구현 설명](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/lmgr/README-SSI)을
2026-09-11 다시 확인했다. 비용의 크기는 작업 부하에 따라 달라지고 모니터링과 재시도 모두
비용이 있다는 점도 [공식 격리 수준 문서](https://www.postgresql.org/docs/18/transaction-iso.html)와 대조했다.
이 판단을 통과시키기 위해 정규식이나 품질 기준을 변경하지 않았다.

## 관측된 교정 비용과 한계

요청 전체는 **31,717ms**였다. 최초 완성 답변과 수정 답변의 기록 시각 차이는
**8,605ms**다. 두 답변의 앞 세 문단은 동일했고 완화책·비용 문단이 바뀌었다.
이는 해당 응답 사슬에서 관측한 변화이며, 필수 교정의 효과나 기본 모델 대비 개선을
추정하는 비교 실험은 아니다. 정상 사례의 불필요한 수정 여부도 미검증이다.

총 사용량은 입력 28, 캐시 생성 입력 15,774, 캐시 읽기 입력 27,192, 출력 2,694 tokens다.
출력 상세의 thinking 952는 출력에 별도로 더하지 않는다. 고유 API 응답은 세 개였고,
마지막 교정 응답은 입력 10, 캐시 생성 입력 925, 캐시 읽기 입력 14,849, 출력 814 tokens였다.
수치와 시각만 보존했으며 hidden thinking 본문을 복사하지 않았다.

## 원인 조사와 준비한 진단 사본

설치된 Claude 실행 파일의 정적 경로는 MCP `content` 배열을 `tool_response`로 전달함을
뒷받침한다. rc.12의 배열 정규화도 두 형식의 로컬 재생을 통과했다. 그러나 실제
hook stdin을 수집하지 않았고, 현재 실패 메시지는 응답 대조·턴 초기화·파일 상태 실패를
구분하지 않는다. 따라서 이번 native 저장 실패를 배열 형식이나 특정 경합 때문이라고
확정할 수 없다.

로컬에서는 턴 초기화 없이 도구 결과가 오거나, 초기화 뒤 SessionStart가 상태를 비우면
같은 실패 메시지가 발생하는 반례를 확인했다. 이것은 가능한 실패 경로의 재현이며
실제 호스트가 그 순서로 실행했다는 증거는 아니다.

별도 `0.2.0-rc.12+diagnostic.85` 사본은 `scenario-evidence.cjs`의 stderr에 고정 단계명,
제한된 형식·개수·불리언 값, 허용 목록의 오류 코드만 기록한다. 원문 입력·응답·초안·
프롬프트·경로·세션 식별자·임의 오류 문구를 기록하지 않는다. 정상 stdout와 저장·거부·
교정 동작은 바꾸지 않는다. 변경된 파일은 해당 훅과 버전 식별용 양쪽 manifest뿐이다.

전체 객체, content 배열, 응답 변조, 초기화 누락, 뒤늦은 SessionStart, 잘못된 인자,
잘못된 JSON의 **일곱 사례**에서 고정 rc.12와 stdout가 같고 필요한 단계가 구분됨을
확인했다. 최초 진단 검사에서 빈 디렉토리가 남는 사례의 결과를 `absent`로 기대했으나
실제 구현은 `unavailable`을 반환했다. 기대 상태를 구분한 뒤 동일한 거부·출력 일치 검사를
통과했으며 제품 코드는 바꾸지 않았다.

## 복원·검사·남은 출하 범위

양쪽 시험 설치와 마켓플레이스를 정상 CLI로 제거했다. 플러그인 목록이 설치 전과 같고,
이번 Codex 신뢰 기록 여덟 개만 정상 설정 API로 제거한 뒤 기존 설정과 비교했다.
이번에 생성된 빈 Claude 설정 및 Codex ON 상태 파일을 원래의 부재 상태로 복원했다.
기존 Codex 표식과 2026-09-08의 기존 TTAK ON 상태는 보존했다. 다섯 native 요청과
프로필 작업의 Windows Job 종료를 확인했으며 잔류 프로세스는 없었다.

이번에는 제품 코드가 바뀌지 않아 관련 Node **23개**와 실제 결과 재생 여섯 조합을 다시
검사했다. 별도 진단 사본의 일곱 사례도 통과했다. 전체 **Node 219개·Python 78개·
conformance** 통과는 제품 바이트가 같은 84의 관측이다. 전체 검사를 이번에 다시 실행한
것으로 보고하지 않는다. 원격 CI·등록 검증·전체 네 기능 비교·게시도 수행하지 않았다.

개발·검토·설명·진행의 원래 기준은 유지한다. 현재 설치와 로컬 회귀 증거가 있어도,
설명의 전달·정밀성 실패 때문에 전체 비교 진입을 권고할 수 없다. Luna의 실제 설명,
정상·미사용 사례, 반복 재현성과 기본·원본 대비 개선은 여전히 미검증이다.
