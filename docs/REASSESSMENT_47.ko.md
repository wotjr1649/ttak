2026-09-09. **시험 입력 준비, 모델 호출 0회, 제품 변경 없음.**

후속 로컬 구현: [두 역할의 출력·결합 계약](REVIEW_ROLES.md)과 별도 실행부를 추가했다.

항목 중 출력 검증과 구조적 결합은 구현됐지만 실제 CLI 연결과 의미상 판정은 미검증이다.
보존한 `operator/plan.json`과 manifest는 준비 당시 기록이며 덮어쓰지 않았다.

후속 [진단 48 네이티브 연결 검사](NATIVE_REVIEW_TRANSPORT.md)에서 두 호스트 각각 1회를
실행해 실제 모델·effort·프롬프트와 프로세스 정리를 확인했다. 현재 진단 잔여량은
25회(선별 시험 18회 + 미배정 7회)다. 아래 27회/9회는 진단 47 준비 시점 기록이다.

최신 [진단 49](ROLE_SCREEN_49.ko.md)는 첫 Claude 근거 검토에서 U014의 필수 오류 문장이
누락돼 1회 호출 뒤 중단했다. 현재 진단 잔여량은 24회이며 나머지 선별 작업은 미실행이다.

## 이번에 정한 방향

사용자와의 grilling에서 문단별 독립 검토를 효과로 채택 여부를 결정할 후보로 두었다.
기존 구현은 보존한다. 네 기능, 품질 기준, Windows 양 호스트, 고정 모델,
구독 인증과 기존 사용량 상한은 유지한다. 검토가 중단되면 확인된 부분과 한계를
전달하고 미확인 핵심 결론은 보류한다. 이는 완전한 설명을 요구하는 출하 과제의
실패를 통과로 바꾸는 예외가 아니다.

새 가설은 전체 초안에 대한 **근거 대조와 문맥 대조의 책임 분리**다.
두 작업자는 상대의 답변을 보지 않고 각각 새 세션에서 전체 문서를 받는다.
근거 대조는 사실 주장과 출처의 관계를, 문맥 대조는 전제·조건·행동·결과 사이의
충돌을 기록한다. 두 역할 모두 전체 문단을 대상으로 한다.

현재 달라진 것은 설계이며 효과의 증거는 없다. 과거와 역할·세션 수·출력 형식이
함께 달라지므로 이 시험은 원인을 분리하는 ablation이 아니다. 기존 독립 검토보다
우수하다고 판정할 수 없고, 연결 구현에 투자할 가치가 있는 후보인지 선별한다.
새 출력 계약이 역할별 근거와 문맥 관계를 실제로 기록하지 못한다면 지침 문구만
바꾼 재시도이므로 네이티브 시험을 시작하지 않는다.

## 준비한 입력과 판정 기준

작업 트리의 `.superpowers/reassessment-47/`에 준비했다. 이 경로는 기존 정책대로
gitignore 대상이며 외부에 게시하지 않는다.

| 입력 | 구성 | 성공·실패 판정 |
|---|---|---|
| case-a | 진단 41과 정확히 같은 과제·초안, 16문단. 검토한 공식 근거 요약 제공 | Oracle/SQL Server 혼동, 집계 쿼리 잠금, 잠금 대기 후 snapshot 갱신 주장의 필수 오류를 찾고 올바르게 수정해야 한다. 이후 전체 문맥을 두 새 역할 세션에서 재검토한다. |
| case-b | 이번에 작성한 정상 대조, 16문단. 동일한 과제·근거 세트 | 잘못된 오류 판정이나 불필요한 수정을 요구하면 실패. 이의가 타당하면 대조 입력 자체를 무효로 판정하고 버전을 새로 만든다. 기존 실행을 성공으로 바꾸지 않는다. |
| case-c | Python `itertools.groupby` 설명, 2문단. 정렬 및 그룹 iterator 수명 오류 포함 | 두 오류와 잘못된 결과 예측을 탐지해야 한다. 검토까지만 배정하며 수정 효과는 판정하지 않는다. |

case-a는 과거 프롬프트 JSON의 문자열에서 복원했고 진단 41의 프롬프트 문자열과
일치시켰다. 원본 전체를 유지하며, 알려진 오류 문단만 골라 전달하지 않는다.
과거의 기대 오류 목록은 최소 기준이다. 그 밖의 정당한 오류를 지적했다고 실패시키지
않으며, 검토 이유와 실제 수정도 공식 근거에 대조한다.

case-b는 기존 초안의 최소 수정본이 아니다. 길이와 표현 차이가 있으므로 엄밀한
짝 대조나 오류율 추정으로 해석하지 않는다. 각 문단의 근거 또는 가정 구분은
`operator/criteria.json`에 있다. SQL과 transaction 설명은 정적으로 검토했으며
데이터베이스를 실행하지 않았다.

case-c는 과거 진단에 사용하지 않은 이번 작성 입력이다. 설계자에게 내용과 정답을
숨긴 holdout은 아니다. 작업자에게 기대 판정을 숨기고, 이 입력으로 수정한 후보가
같은 입력을 다시 통과해도 일반화 증거로 세지 않는다.

공식 문서는 2026-09-09 확인했다. 짧은 자체 요약을 사용하며 실제 원문 검색 능력은
시험하지 않는다. 근거는 [PostgreSQL 18 isolation](https://www.postgresql.org/docs/18/transaction-iso.html),
[SELECT locking clause](https://www.postgresql.org/docs/18/sql-select.html),
[Oracle 21c concurrency](https://docs.oracle.com/en/database/oracle/oracle-database/21/cncpt/data-concurrency-and-consistency.html),
[SQL Server isolation](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17),
[Python 3.14 groupby](https://docs.python.org/3.14/library/itertools.html#itertools.groupby)다.
평가 기준은 이 에이전트가 작성했다. 독립 인간 전문가의 검토나 완전한 정답표로
표현하지 않는다. case-c의 구체적 결과는 별도 로컬 실행으로도 확인했다.

## 호출 장부와 중단

| 입력 | Claude 최대 | Codex 최대 | 합계 |
|---|---:|---:|---:|
| case-a: 근거 검토 + 문맥 검토 + 수정 + 두 역할의 전체 재검토 | 5 | 5 | 10 |
| case-b: 근거 검토 + 문맥 검토, 오류 판정 시 수정 전에 중단 | 2 | 2 | 4 |
| case-c: 근거 검토 + 문맥 검토 | 2 | 2 | 4 |
| 구성요소 시험 | 9 | 9 | **18** |
| 기존 진단 잔여량 중 미배정 | | | **9** |

앞서 제안한 24회는 정상 대조의 수정·재검토까지 포함했다. 오탐 즉시 중단과 충돌하므로
그 6회를 제거했다. 18회는 전부 실행해야 할 할당량이 아니다. case-a부터 호스트별로
두 검토와 필요한 수정·재검토를 검증하고 case-b, case-c로 진행한다. 각 역할 결과를
확인하고 중대한 실패가 발생하면 다음 호출 전에 전체 후보 시험을 중단한다.
한 호스트가 실패하면 다른 호스트의 결과로 상쇄하지 않는다.

Claude는 `claude-sonnet-5 / medium`, Codex는 `gpt-5.6-luna / high`다.
모든 호출은 새 transport 세션, 순차 실행, 재시도 0회를 전제로 한다. 호출당 120초,
stdout 1 MiB, stderr 64 KiB, 종료 정리 10초를 제안했다. **아직 구현·검증된 제한이
아니다.** 18 × 120초인 36분은 호출 timeout 합계일 뿐 실제 지연 예측이 아니다.
종료 정리와 사람의 판정 시간은 별도다.

장부의 모든 `attempts`는 0이다. 추가 활성화·조회·채점·연결 확인에 모델을 사용하면
별도 행으로 먼저 계산하며 기존 27회 안에서 배정한다. 미배정 9회는 자동 재시도나
실험 확장에 쓰지 않는다. CLI 호출, 내부 요청, input/output/cache 토큰, 경과 시간은
각각 기록한다. 구독 잔여율이나 금액으로 환산하지 않는다.

한도·인증·권한 문제, 모델/effort/세션 확인 실패, 알려진 중대한 오류 누락, 잘못된
수정, 새 오류, 실제 coverage 누락은 중단 사유다. 새로운 정당한 이의는 독립 근거로
판정하고 기록하며, 기존 원자료나 기대 기준을 소급 변경하지 않는다.

## 실제 실행 전에 남은 일

1. 로컬 출력 계약은 `review-roles.cjs`에서 검증한다. 이를 네이티브 작업자의 일반
   프롬프트·출력 형식에 연결해야 한다. 문단 열거만으로 모든 주장을 찾았다고 주장하지 않는다.
2. 구조적 중복·충돌·겹치는 인용은 로컬에서 처리한다. 동일 인용의 두 오류 이유가
   의미상 충돌하는지는 기계적으로 판정하지 못한다. 이를 실제 판정 경로에서 검토해야 한다.
   새 `review-role-workflow.cjs`가 기존 인용·수정 검사를 재사용한다. 이전 문단별
   `review-workflow.cjs`는 그대로 보존했다.
3. 실제 CLI 경로와 model/effort/session 감사, 프로세스 정리는 진단 48의 짧은 근거 역할
   검사에서 확인했다. 전체 두 역할·수정·재검토는 선별 시험에서 확인해야 한다.
4. 실행 계약까지 고정한 **별도 manifest**를 만들고 모든 호출을 재계산한다. 이번 manifest는
   입력의 무결성만 고정한다. 기존 release-run-23과 이번 manifest를 덮어쓰지 않는다.

worker-inputs는 `schema_version`, `task`, `draft`, `references`만 담는다.
기대 판정·과거 기록·장부·원자료 경로는 operator 파일로 분리했다. 이 파일 분리만으로
네이티브 격리가 증명되지는 않는다. 실행 시 operator 파일을 읽을 수 있는 도구나
프로필·인증 자료 접근을 작업자에게 제공하지 않아야 한다. 작업자 출력은 명령·경로·
수신자를 선택할 수 없다. MCP 등록이나 플러그인 설정 변경은 이 준비에 포함하지 않는다.

## 전체 출하 비용에 미치는 영향

기존 32개 응답 투영에 두 역할 검토를 모두 적용한다고 가정하면, 기존 비교 516회에
64회가 추가되어 **580회**다. 모든 응답에서 한 번 수정하고 두 역할이 전체 재검토하면
516 + 32 × 5 = **676회**다. 두 번 수정·재검토하면 516 + 32 × 8 = **772회**다.
이는 새 후보 출력, 근거 수집, 최종 전달, 실패 비용까지 관측한 상한이 아니다.
검토가 적용될 실제 응답 범위도 설치 동작으로 확인해야 한다.

따라서 이 구조도 기존 전체 비교 배정 516회에 들어간다고 볼 수 없다. 과거 결과
재사용 자격은 미검증이며 차감하지 않는다. 구성요소 시험이 통과하더라도 제품 연결·
현재 후보 반복 비교를 거친 뒤에만 출하를 판정한다. 다음 예산 제안은 그때 확보한
사용량 근거를 포함해야 한다.
