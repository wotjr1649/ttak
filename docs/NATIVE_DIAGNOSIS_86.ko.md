# 실제 경계 진단 86 — JSON 문자열 응답 확인

후속 [통합 검증 87](NATIVE_VALIDATION_87.ko.md)에서 아래 수정안을 제품에 반영하고
전체 로컬 검사를 통과했다. 실제 Haiku 필수 교정은 동작했으나 최종 Q1이 실패해
5회 사용·7회 미실행으로 중단했다. 아래는 통합 전 진단 86 시점의 기록이다.

승인된 **Haiku native 요청 2회 진단을 완료**했다. 실제 `PostToolUse.tool_response`가
문자열인데 훅이 그 형식을 거부하는 지점을 확인했다. 턴 상태는 초기화돼 있었고 Stop의
턴 비교도 일치했다. 84의 배열 가정은 실제 전달 형식을 충분히 추적하지 못한 판단이었다.

문자열을 기존의 정확한 결과 대조로 처리하는 **별도 rc.13 검토 사본**을 준비했다.
실제 기록 재생과 관련 검사 25개는 통과했지만, 이 수정안은 제품 본체에 반영하거나
설치·native 실행하지 않았다. 출하 판정은 여전히 **No-Go**다.

## 범위와 결과

사용자의 다음 권고 진행 확인에 따라 [검증 85](NATIVE_VALIDATION_85.ko.md)에서 준비한

수집기와 상대 require 경로 14개 및 실행 파일 해시도 별도로 고정했다.

Claude Code `2.1.266`, Node `24.19.0`, 모델 `claude-haiku-4-5-20251001`을 사용했다.
thinking 8192는 요청값이며 실제 한도 적용을 확인한 값은 아니다. 기존 구독 프로필만
사용했고 추가 모델·API fallback은 없었다. 이번에는 Codex 설치·설정·모델 작업을 하지 않았다.

## 실제 실패 지점

진단 사본의 고정 단계 기록에서 다음을 확인했다.

| 단계 | 실제 기록 | 의미 |
|---|---|---|
| 입력 수신 | `bad:false`, `within_limit` | 입력 크기 초과나 수신 실패가 아님 |
| 이벤트 | `enabled:true`, 유효한 session, data root 존재 | ON 상태에서 정상 도구 이벤트 진입 |
| 인자 | `exact_keys:true` | 요구한 도구 인자 키와 일치 |
| 응답 형식 | `container:"string"`, `content_count:null` | 전체 MCP 객체나 content 배열이 아닌 문자열 |
| 실패 | `unverified_tool_result` | 지원하지 않는 컨테이너 형식에서 거부 |
| Stop의 상태 조회 | `present:true`, `status:"empty"`, `turn_matches:true` | 턴은 초기화됐지만 검증된 근거가 저장되지 않음 |

원문 hook stdin은 캡처하지 않았다. 대신 동일한 도구 호출의 native 이력에 저장된
`toolUseResult`가 문자열이고, 그 문자열을 JSON으로 읽은 값이 재계산한 도구 결과와
완전히 일치함을 확인했다. 실제 단계 기록과 이 일치 검사가 문자열 경계 진단을 뒷받침한다.
원문 응답·초안·프롬프트·경로·세션 식별자·임의 오류 문구를 진단 로그에 추가하지 않았다.

84의 정적 경로 분석은 중간 값의 `content`를 배열로 가정했으며 실제 훅 입력까지
확인한 증거가 아니었다. 이번 실제 관측을 우선한다. 모든 Claude 도구가 항상 문자열을
보낸다고 일반화하지 않고, 관측된 문자열과 기존 객체·배열을 모두 정확히 검증하는 수정안을 택했다.

## 준비한 최소 수정안

제품 본체의 rc.12를 보존하고 별도 `0.2.0-rc.13` 사본을 만들었다.
`hooks/scenario-evidence.cjs`에서 문자열은 단일 text block으로 감싸고,
배열과 전체 객체는 기존 방식으로 정규화한다. 이후 검사는 공통이다.

- 도구 인자 키와 유한 시나리오 검증
- 단일 text block 및 JSON 파싱
- 재계산 결과와 완전 일치, 객체 형식의 오류·structured 결과 검사
- 턴 격리·파일 보호·유효기간·한 번만 소비하는 교정 경계

실제 native 이력에 저장된 문자열을 로컬에서 재생한 결과는 다음과 같다.
Stop 동작 확인에는 별도 고정 설명문을 사용해 기존 문구 감지 경로와 혼동하지 않았다.

| 입력 형식 | 기존 rc.12 | 제안 rc.13 |
|---|---|---|
| 실제 기록된 JSON 문자열 | 거부, 필수 교정 없음 | 근거 저장, 첫 Stop만 교정 요청 |
| 같은 결과의 content 배열 | 첫 Stop만 교정 요청 | 동일 |
| 같은 결과의 전체 MCP 객체 | 첫 Stop만 교정 요청 | 동일 |

문자열을 무조건 신뢰하거나 임의 객체를 반복해서 풀어 읽지 않는다. 잘못된 JSON,
뒤에 다른 텍스트가 붙은 값, 다른 계산값, JSON으로 직렬화한 MCP wrapper·배열은 계속
거부한다. 실제 패키지 명령에 문자열을 전달해 근거 저장과 한 번의 Stop 요청도 확인했다.

Windows Node 검사 **25개가 통과했고 skip은 0**이다. 실제 기록 재생은 여섯 조합을
통과했다. 테스트 프로세스도 Windows Job 안에서 종료됐고 잔류 프로세스는 0이었다.
새 사본의 native 동작, 전체 회귀, 원격 CI는 아직 실행하지 않았다.
rc.12의 기존 전체 Node 219개·Python 78개·conformance 결과를 rc.13 결과로 바꾸어 보고하지 않는다.

## 사용량·복원·남은 공백

전문가 설명 요청은 **25,444ms**가 걸렸다. 사용량은 입력 18, 캐시 생성 입력 14,801,
캐시 읽기 입력 12,345, 출력 2,074 tokens다. 출력 상세 thinking 729는 출력에 더하지 않는다.
고유 API 응답은 두 개였다. 필수 교정이 실행되지 않았으므로 이 수치를 그 교정의
추가 비용으로 판단할 수 없다. 이번은 원인 진단이므로 H/Q 출하 판정도 별도로 내리지 않았다.
지원하는 문구 검사가 최종 문제를 찾지 못한 것 역시 품질 합격을 뜻하지 않는다.

두 요청 후 시험 설치와 마켓플레이스를 정상 CLI로 제거했다. 설치 전후 플러그인 목록이
일치했고, 시험 데이터와 이번에 생성된 빈 설정 파일을 원래의 부재 상태로 복원했다.
native 요청과 설치·제거 작업은 모두 정상 종료·프로세스 정리를 확인했다.
제품 본체는 rc.12이며 이전 소스·패키지·장부도 보존했다.

다음 권고는 검토 사본의 변경 다섯 파일(훅·양쪽 manifest·관련 테스트 두 파일)을 제품에
반영하고 전체 로컬 검사를 통과시킨 뒤, **새 native 검증 최대 12회**를 수행하는 것이다.
OFF/ON 4회와 기존의 전문가·미사용·정상·반복 품질 8회이며 첫 실행·전달·실질 품질 실패에서
남은 행을 중단한다. Haiku/Luna와 두 CLI의 정상 플러그인 흐름 및 원래 H/Q 기준을 유지한다.
전체 비교 516회·추가 모델·게시로 자동 확대하지 않는다. 이 다음 단계는 새 확인 전 실행하지 않는다.

고정 입력·단계 기록·실제 결과 대조·검사·복원 증거는 이 worktree의
`.superpowers/native-diagnosis-86/`에 보존한다. 검토 사본은 `fix-candidate/ttak/`에 있다.
이 경로는 ignored이므로 HEAD만으로 실행과 수정안을 재현할 수 있다고 주장하지 않는다.
