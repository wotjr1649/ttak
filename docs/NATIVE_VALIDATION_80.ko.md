# rc.10 실제 모델 답변 검증 80

2026-09-10. **rc.10의 첫 Haiku 답변은 정밀성 Q1에 실패했다.**
두 독립 채점자가 동일한 최종 답변을 불합격으로 판정했고 root가 원래 기준으로 확정했다.
이번 기록은 실제 후보의 실패 관측이며, 모델 전체나 다른 호스트의 실패를 뜻하지 않는다.

## 고정 계획과 실행

사용자의 실제 모델 검증 요청에 따라 기존 장부와 별도로 네이티브 호출 상한 4회를
설정했다. 순서는 Haiku 1 → Luna 1 → Haiku 2 → Luna 2이며 각 실행은 새 세션이다.
첫 실행 오류 또는 실질적 품질 실패 시 나머지를 중단하도록 고정했다.
후보는 rc.10, 질문과 H1–H3/Q1–Q2는 원래 `explain-expert` 과제 그대로다.
후보·입력·드라이버·바이너리 해시를 고정했으며 실행 중 제품은 수정하지 않았다.

첫 Haiku 실행에서 확인한 사항:

- Claude Code `2.1.266`, 모델 `claude-haiku-4-5-20251001`, sidechain 없음.
- 정상 ON 정책과 정확한 skill 본문 전달.
- 실제 MCP 호출 1회, 계산 응답의 재계산 일치, 구현 근거 **2개 실제 전달**.
- 마지막 assistant 본문과 native 최종 결과 일치.
- Stop 1회가 `hook_success`, `stdout={}`, exit 0으로 완료. **교정은 0회**.
- 네이티브 실행 약 33.8초, exit 0, Windows Job 정리 확인, 남은 자식 프로세스 0개.
- thinking 존재는 관측했지만 요청 상한 8192의 실제 적용은 독립적으로 입증하지 못함.

도구와 hook의 정상 종료는 답변의 정확성을 뜻하지 않는다.
특히 79와 달리 이번에는 근거가 실제로 전달됐으므로, 근거 전달 누락만으로
최종 답변의 오류를 설명할 수 없다.

## 독립 검토와 판정

서브에이전트 세 개에 각각 기준 감사, 반례 검토, 실행 증거 검토를 맡겼다.
두 채점자에게는 모델·후보명을 가리고 답변의 실질 내용 전체를 일반 텍스트로 전달했다.
원래 Markdown 답변과 해시는 로컬 실행 기록에 보존했다.
root는 의견을 단순 집계하지 않고 실제 답변·계산·원래 기준과 대조했다.

| 항목 | 기준 감사자 | 반례 검토자 | root 최종 |
|---|---|---|---|
| H1 원래 snapshot | 통과 | 통과 | 통과 |
| H2 다른 쓰기 대상에도 불변식 위반 | 통과 | 통과 | 통과 |
| H3 유효한 완화책 | 통과 | 실패 | 통과 |
| Q1 정확한 용어·구체적 실행 설명 | 실패 | 실패 | **실패** |
| Q2 동시성·재시도 비용 | 통과 | 통과 | 통과 |

H3 차이는 추가로 제안한 커밋 후 재검사를 어디에 집계하는지의 차이다.
root는 유효한 Serializable 제안 자체로 H3를 통과시키고, 부가 설명의 오류를 Q1에
반영했다. 이 차이는 전체 불합격 판정에 영향을 주지 않는다.

Q1의 구체적 문제는 다음과 같다.

1. 예시에서는 각 트랜잭션이 두 행을 모두 읽었는데, 원인 설명에서는 서로 다른
   행을 읽는다고 서술해 읽기 집합과 쓰기 대상의 구분이 흐려졌다.
2. 직렬화 가능한 결과와 실제 관측 순서를 구분하지 않고, 나중 트랜잭션이 앞선
   commit을 보게 된다는 설명을 일반적인 보장처럼 제시했다.
3. 읽기/쓰기 의존성 추적과 cycle 탐지를 모든 Serializable 구현의 동작처럼 설명했다.
4. 커밋 뒤 불변식을 재검사하고 retry하는 방식을 덧붙였다. 이는 이미 커밋된
   SI 불변식 위반을 일반적으로 예방하는 방법이 아니다.

단순히 특정 데이터베이스 이름이나 성능 수치가 없다는 이유로 실패시키지 않았다.
두 원래 snapshot, 서로 다른 쓰기 대상, 의사 0명이 되는 결과와 재시도 비용의
올바른 설명은 통과로 보존했다.

## 중단·장부·증거

나머지 Luna 1, Haiku 2, Luna 2는 최초 품질 실패로 **미실행**이다.
따라서 Luna의 rc.10 품질과 두 호스트의 반복 재현성은 미검증이다.
전체 비교 192개 과제, Opus/Sol, 출하 검증으로 확장하지 않았다.
임시 ON 상태는 원래의 상태 파일 없음으로 복구했고 후보 코드는 그대로 보존했다.

이번 별도 검증 상한 4회 중 **1회 사용, 3회 미사용**.
누적 네이티브 진단은 **707회(Claude 421, Codex 286)**.
전체 비교용 **516회는 미사용**이다. 서브에이전트 검토는 이 네이티브 CLI 장부와
별도이며 대상 모델의 독립 실행 반복으로 계산하지 않는다.

증거는 `.superpowers/native-validation-80/`의 `plan.json`, `candidate/`,
`ledger/01.haiku.known/result.json`, `delivery-audit.json`, `operator-review.json`,
`independent-reviews.json`, `outcome.json`, `state-restored.json`에 보존했다.
이 실행을 같은 후보의 성공 사례가 나올 때까지 재시도하지 않았다.
